## 1. 模組概述
- 頁面：`views/QC/tool_calibration.php`（量測儀器校驗管理）。
- 目的：管理量具（量測儀器）的校驗週期與校驗紀錄，作為 KPI #18 的資料來源。
- **核心機制：主檔週期自動推算到期**。每支量具設「校驗週期(月)」與「基準下次應校驗**月**」；每次登錄校驗完成，系統自動把「下次應校驗月」前滾為 `校驗月 + 週期`。
- **到期一律以「月」為單位**（2026-07-30 使用者定調：同一月份內安排校驗即可）：`calibration_due` / `due_date` / `next_due` 一律存**該月 1 日**，畫面顯示 `YYYY-MM`，欄位用 `<input type="month">`；**準時＝實際校驗日 ≤ 該到期月月底**(+grace)。工具函式：`tool_calib_month_start()` / `tool_calib_month_end()` / `tool_calib_next_due_month()`（新寫程式一律用這三支，不要自己算日期）。狀態：到期月已過＝逾期、本月或下月到期＝即將到期。
- 儀器主檔沿用既有 `qc_tool`（量具表），僅**加欄**，未動既有資料。

### 3b. 量具料號對應（`qc_tool.purchase_spec_id` → `purchase_spec`）
**使用者 2026-07-30 定案，勿自行改方向**：
- **不另建量具規格主檔**。量具的規格掛到**採購料號**：`purchase_item`（品項＝量具類別，如「盤式分厘卡」）→ `purchase_spec`（規格變體＝真正的採購料號 `spec_code`）。理由：全公司只留「採購料號」與「產品料號」兩種比較單純，且**入庫未領的量具也查得到**。
- **實體仍以量具編號 `qc_tool.Tool_No` 為主**（同規格同廠牌會有多支），再往上指向規格；`Tool_No` 既有值一律不動。
- **校驗週期維持「依類別設定」**（`bulk_set_cycle`），不改成依規格帶入。
- 舊資料的規格是人工塞在編號字串裡（`A-200-Q 電子(0-25mm)`、`B-007-Q (0-300mm）` 半形全形混用），所以**先解析成草稿給使用者確認、可改，確認後才寫入**（`spec_draft` → `spec_apply`，不可直接寫）。
- 解析規則（`tool_calib_parse_tool_no()`）：規格＝**最後一組括號內容**（半/全形皆可）；型式＝編號出現「電子」→ 電子，否則機械（「電子式」會整段去掉不重複算）；型號＝去掉編號本體與「電子(式)」後剩下的字（例 三點式、千分），**與類別同名時視為贅字捨去**；**廠牌編號看不出來，一律留空待使用者補**。
- 寫入的 `spec_text` 由 `tool_calib_compose_spec_text()` 組出＝`規格 型號 電子`（空欄略過，上限 150 字）；前端 `spCompose()` 是同一套組法，改一邊要改兩邊。**品牌不併進 spec_text**，是 `purchase_spec.brand` 獨立欄位（見下）。
- **品牌 ≠ 購買廠商**（使用者 2026-07-30）：品牌是「誰做的」（存 `purchase_spec.brand`，字串不綁 id），廠商是「跟誰買的」（`purchase_spec_vendor`，同規格可多家）。**兩者的維護畫面都在「申請採購 → 採購品主檔」**，本頁只能選現有品牌或手動打字（`spec_draft` 回 `brands`，畫面用 `<datalist>`）。
- **單位預設 PCS**（`tool_calib_default_unit_id()` 找 `stock_units` 的 PCS）；沿用既有料號時只補「目前空白」的單位，已設定過的不覆寫。
- **批次自動建立**：`spec_apply` 帶 `auto=1`＋`scope=unbound|all`，後端直接用自己解析的草稿整批建立，不需逐列確認（品牌留空）。
- **冪等**：同 category＋同 `item_name` 沿用既有品項；同 `item_id`＋同 `spec_text`＋**同 `brand`** 沿用既有規格（不同品牌＝不同料號），重跑草稿與重按建立都不會產生重複料號。品項碼／料號碼一律呼叫 `purchase_lib.php` 的 `purchase_next_item_code()` / `purchase_next_spec_code()`（編碼規則唯一來源，勿自己拼）。
- `purchase_item.category_id` 必填，指向 `stock_item_categories`；預設挑 `category_code='QC'`（品管 檢/量具），畫面上可改。
- 目前 75 支量具中有 8 支編號看不出規格（`hh`、`J`、`M-001~041-Q`、`QC-001/002/004/005/008`），草稿會標紅提示「編號看不出規格，請自行填寫」；留空也可建立，同類別的空白規格會共用同一個料號。

## 5. KPI 計算（tool_calib_lib.php `tool_calib_kpi_compute`）
月份 M：
- **den（當月應校驗）** = ①已完成紀錄 due_date 落在 M 者 ＋ ②主檔 calibration_due 落在 M 且尚無對應紀錄者（尚待完成）。
- **num（準時完成）** = ① 中 calib_date ≤ due_date(+grace_days 寬限，參數) 者。
- value = den>0 ? num/den*100 : null。
- 僅計 `calib_managed=1` 的量具，且**其類別 `qc_tool_list.calib_required` 須為 1**（欄位存在才加此條件，尚未升級 schema 時行為與加欄前相同）。
- registry key `calibration_ontime`（參數 grace_days，預設 0）；指標 #18 source_mode=auto。

## 10. 已知注意事項/設計要點
- **前滾邏輯**：record_calib 時 due_date = 當下 calibration_due（可能為 null），next_due = calib_date + 週期；並 UPDATE qc_tool.calibration_due = next_due。edit_calib 若編輯的是「最近一次」紀錄才會再前滾主檔。delete_calib 會依剩餘紀錄修復 calibration_due。
- **準時判定**：on-time = calib_date ≤ due_date(+grace_days)。逾期補做（calib_date>due）計 den 不計 num。
- qc_tool 為既有 QC 量具表，其他頁（如檢驗）也用 Tool_No，**勿刪欄或改既有欄語意**，只加欄。
- **類別旗標是跨頁的**：`has_tool_no=0` 的種類，在 `inspection_combined_prototype.php`「量具設定」也會隱藏「新增編號」表單並在 `save_tool_instance` 後端擋下（該頁不含 tool_calib_lib，欄位查詢用 try/catch `PDOException`，欄位不存在時不擋以維持舊行為）。改旗標語意時**兩頁都要看**。
- `calib_required=0` 只是不列入本頁/KPI，**不影響**該類別當作檢驗方式使用（`qc_inspection_item_tool_type` 照舊），所以「目視」仍能在檢驗項目挑選。
- **批次校驗與單筆登錄共用同一套前滾規則**（due_date＝登錄當下主檔到期日、next_due＝校驗日＋週期），所以 KPI 不因走批次而有差異；批次的每一列紀錄都能單獨在歷史 modal 編輯/刪除。
- **附件不可存絕對路徑**（鐵律5）：新增任何附件相關功能時，一律呼叫 `tool_calib_attach_file()`，不要在其他地方自行 `dir . file`。附件在批次存檔前是 `temp`（`batch_id=0`），對外讀取（list/history/batch_detail）一律只取 `active`。
- 上傳大小另受 PHP `upload_max_filesize`／`post_max_size` 限制，附件設定的 MB 上限只是應用層再收一次；使用者若回報大檔上傳失敗要一起看 php.ini。
- **必填是 2026-07-30 才加的**：在此之前登錄的舊紀錄可能 `operator` 為 NULL（年度紀錄會顯示「—」），屬正常歷史資料，不要當成 bug 去回填。
- **畫面用語**：`calib_managed` 欄位語意不變，但畫面一律稱「**列入校驗率統計**」（原「納管／納入管理」已全面改字，2026-07-30）。改字時請連 CSV 標題、狀態 pill（`unmanaged`＝未列入統計）、篩選選項一起改。
- 年度計畫表的計畫月份是**推算**而非另存一張排程表：以主檔 `calibration_due` 為錨點，用週期往前後推（含歷史紀錄 due_date）。所以調整週期或基準日後，過去年度的計畫圖也會跟著重算——這是刻意的（單一真相來源），若日後要凍結年度計畫需另設快照表。
- `calibration_due` 是既有欄位，本模組賦予「下次應校驗日」語意並自動維護。
- **清除測試資料的刪除範圍是刻意收斂的**：只清 `qc_tool_calibration`／`qc_tool_calib_batch`／`qc_tool_calib_attach`（含實體檔）／`qc_tool_calib_attach_map`，並把 `qc_tool` 的 `calib_cycle_months`／`calibration_due`／`calib_managed`／`calib_method` 還原為空。**不動**類別旗標與自訂分頁（`qc_tool_list`、`qc_tool_calib_tab`）、附件設定（`system_settings` 的 `tool_calib_*`）、校驗人員資格（`qc_tool_calib_staff`）、量具主檔本身與 `purchase_spec_id`。要加刪除對象前先確認使用者同意，這是不可回復的操作。
- **附件實體檔的路徑要在刪 DB 列之前算好**（列刪掉就查不到檔名了），且一律走 `tool_calib_attach_file()`；unlink 放在 commit 之後，交易失敗時不會誤刪檔案。
- **交易中不可呼叫 `jerr()`**（它 `exit` 而不 rollback）→ `spec_apply` 迴圈內的驗證改丟例外，交給 catch 統一 rollback。新增交易內的驗證時要照這個寫法。
- 量具料號對應**不改 `Tool_No`**，也不動線上檢驗頁對 `qc_tool` 的既有使用；`purchase_spec_id` 只是多一個可為 NULL 的欄位，未對應時全站行為與加欄前相同。
- **MySQL 的 DDL 會觸發隱含 commit**：`purchase_ensure_brand_vendor_schema()` 內含 CREATE/ALTER，**絕對不可在 `beginTransaction()` 之後呼叫**——交易會被做掉，之後 `commit()` 直接噴「There is no active transaction」，而且前面寫入已無法 rollback。本專案已踩過一次（2026-07-30 `spec_vendor_save`），所以 `purchase_save_spec_vendors()` 刻意不建表，由呼叫端在交易外先確保 schema。
- 品牌是「名稱字串」不是外鍵：品牌清單改名不會連動既有規格（刻意），刪除時若已被規格使用會自動改成停用而不是刪掉。
