# 19. 核准人員解析規則（部門內任一主管／固定關鍵人員／AS文件所屬部門自動判斷）

> 2026-08-06 制定，使用者明確要求全站適用。起因：供應商稽核計劃的核准人員原本寫死用 `org_role_lib.php` 的單一 `top_approver`（全站只有一個「最高核准人員」），但使用者要的是「這張表單自己的核准人」——可以是某部門內任一主管、也可以固定某個關鍵人員、都沒設時要能自動判斷，不是每個表單都共用同一個人。
> 唯一參考實作：`src/common/org_role_lib.php`（`dept_or_user` 綁定類型）＋`src/common/vendor_audit_lib.php` 的 `vendor_audit_plan_approver_pool()`；設定入口 `views/admin/org_role_setting.php` 第三節「部門或人員擇一綁定」。
> 2026-08-10 補充第五節「進階：可設定優先序鏈＋強制 SoD 迴避」，使用者明確要求（見下）。

## 適用情境

任何表單/流程要決定「送出後誰能核准」，且核准人**不是全站固定同一人**（那種情況直接用 `org_role_lib.php` 既有的 `type=user` 綁定即可，例：`top_approver`），而是**依這張表單自己的業務歸屬**決定核准人時，一律照本規則做，禁止各模組自己寫死部門 id 或人名、禁止自己重新發明一套解析邏輯。

## 三段式解析順序（依序判斷，第一個成立就用它，不再往下）

1. **綁「部門」**：`org_role_lib.php` 新增的 `type='dept_or_user'` 角色，管理員在設定頁指定一個部門。核准人＝**該部門（含子部門）內所有職級不低於送出者的主管**，任一人核准即生效（OR-gate，不是只認職級最高的那一個人）。
   - 「職級不低於送出者」＝核准人的 `position_level.level` 數字要 **≤** 送出者的 `level`（數字越小職級越高，經理=1 > 課長=2 > 組長=3）；送出者本身沒有主管職級（非管理職）時視為無下限，該部門任一主管都合格。
   - 送出者的職級一律用 `eg_user_main_identity($db, $uid)['level']`（`delegate_lib.php`），不要另外發明判斷方式。
2. **綁「人員」**：管理員直接指定固定某一人核准（適合本來就该由特定人核決的表單）。
3. **都未設定**：自動抓**這張表單目前綁定的 AS 文件**（`as_document.department_id`，經 `asdoc_lib.php`/`eg_asdoc_get()` 或模組既有的 `xxx_bound_asdoc()` 取得）所屬的部門，套用第 1 點同一套「部門內任一主管、職級不低於送出者」規則。這樣即使管理員完全沒特別設定，只要 AS 文件本身有指定歸屬部門（文管中心設定時填的），也能自動解析出合理的核准人，不會卡在「沒人核准」。

三段都解析不到（部門/人員都未設、AS 文件也沒歸屬部門、或部門內找不到任何主管）→ 回傳空陣列，呼叫端要擋下並提示管理員先去設定，不可放行成「沒人核准也算過」。

## 落地做法（照抄 vendor_audit 的三個檔案）

1. **`org_role_lib.php`**：在 `EG_ORG_ROLES` 常數裡新增一筆 `'type'=>'dept_or_user'` 的角色定義（`label`/`desc` 說清楚三段解析順序）。`eg_org_save()` 對這個 type 的處理是「兩者都填時部門優先，人員視為未設定」，不像 `dept`/`user` 兩種既有 type 那樣互相清空對方。
2. **`org_role_setting.php`**：新增「三、部門或人員擇一綁定」表格區塊，同一列**同時放部門下拉與人員下拉**（`deptSel()`/`userSel()` helper 已改成可傳自訂 class 參數 `'or-mix-dept'`/`'or-mix-user'`，避免跟既有的 `.or-dept`/`.or-user` 全域收集邏輯衝突而互相覆蓋）；儲存時**兩個下拉的值要合成同一筆 role_key 送出**，不能像既有兩段各自獨立 push（那樣後端會依 role_key 覆寫，後送出的那段會蓋掉先送出的）。
3. **模組自己的 lib**（如 `vendor_audit_lib.php`）：寫一個 `xxx_approver_pool($db, $submitterUid): array` 依三段解析順序回傳合格核准人清單（`[['id'=>int,'user_cname'=>string],...]`）。呼叫端（API 的 submit/decide 動作）：
   - 送出時：解析池為空 → 擋下並提示去設定；解析出來 → **全部人都收到待核准通知**（`live_event_target` 每人一列，不是只通知一個人）。
   - 核准/退回時：檢查目前登入者是否在**依原送出者職級重新解析出的**池子裡（不是重新用目前操作者的職級算，要用當初送出那個人的職級，因為「不可低於送出者」比較基準是送出者，不是核准者自己），或本身是模組管理員。
   - 通知連結被點開時的頁面權限檢查，改用「這個人是不是某筆待處理通知的實際收件人」（查 `live_event_target` 有沒有這筆），不要再假設只有一個固定的核准人——這樣的檢查更準確，也不用重新解析整批人選。

## 常見誤區

- **不要**只解析出「職級最高的那一個人」當唯一核准人（那是 `eg_org_dept_manager()` 的邏輯，用於「這個部門的窗口是誰」這種單一人選場景）——本規則要的是**一批**都夠格的人，任一人動作即可，這樣主管請假/出差時不會卡關，也不需要另外疊代理系統解析（多人本身就是備援）。
- **不要**把 AS 文件的部門欄位當成強制條件——那只是「都沒手動設定時」的最後備援，管理員一旦在設定頁指定了部門或人員，就不再看 AS 文件綁的部門。
- 送出者本人若剛好也在合格核准人池子裡（自己送出、自己還能核准自己），是否要加簽核迴避（SoD）**依各模組實際需求決定**；`vendor_audit_plan_approver_pool()` 已強制擋（見第五節），其他模組要加時比照同一寫法。

## 五、進階：可設定「優先序鏈」＋強制 SoD 迴避（多來源備援時適用）

當一張表單的核准人來源不只一種、且管理員希望能自訂「先試哪個、找不到再試下一個」時，在前三段解析之外再疊一層**優先序鏈**（唯一參考實作：`vendor_audit_lib.php` 的 `vendor_audit_plan_approver_chain()`／`_chain_save()`／`vendor_audit_plan_approver_pool()`，供應商稽核計劃核准=使用者 2026-08-10 明確要求的落地案例）：

1. **拆成獨立方法**：把「部門或人員綁定」（本規則第一~三段）包成一個方法（如 `dept_or_user`），另外視需要加其他方法，例如：
   - `auto_supervisor`：直接呼叫 `delegate_lib.php` 既有的 `eg_resolve_supervisor($db, $submitterUid)`（同部門更高階主管，找不到就往上一層部門找負責人，請假/採購簽核已在用同一套），**不要自己重寫這段爬升邏輯**。
   - `top_approver`：沿用全站共用的 `eg_org_user($db, 'top_approver')`，不要另開一個獨立設定項——除非使用者明確要求該表單要有自己專屬的最高決策者。
2. **管理員設定優先序**：`system_settings` 存一個 JSON 陣列（方法 key 依序排列），未設定時預設全部方法照某個合理順序全用。設定 UI 用幾個下拉分別選「第一/第二/…順位」，每個下拉可選任一方法或「（不使用）」，儲存時篩掉重複與空值。
3. **依序嘗試，取第一個非空結果**：`foreach ($chain as $method) { $pool = 解析該方法(...); if ($pool) return $pool; }`，不要把所有方法的結果合併——那樣會混進不同信任層級的人（例如部門主管和最高決策者同時出現，語意會亂）。
4. **SoD 強制擋**：每個方法解析出來的池子，都要先濾掉送出者本人（`array_filter($pool, fn($p) => $p['id'] !== $submitterUid)`）再判斷是否為空——解析到本人視同該順位無結果，自動落到下一順位，不需要另外寫「找不到就再找一次」的迴圈。這是本規則第四節「未強制」的具體落地方式，凡是新表單要做球員兼裁判迴避，照這個寫法即可。
