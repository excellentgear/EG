# 共用帳號：成員綁定與通知轉送 製作說明（給 AI）
> 最後修改：2026-07-29 — 首版（需求定案，尚未實作）。動工前必讀 CLAUDE.md 鐵律＋本檔。
> 讀者：要實作「現場共用帳號」成員綁定、通知轉送、密碼鎖定的 AI session。

## 0. 背景與需求（使用者原話整理）
- 現場大多數員工用**共用帳號**登入（例如各廠區一台平板一個帳號），個人帳號幾乎不開。
- 通知（live_event → Web Push / Telegram / 站內清單）目前只送「員工本人帳號」→ 用共用帳號的人**收不到**。
- 需求：可設定「哪些員工使用哪個共用帳號」，通知該員工時自動轉送到共用帳號；**因多人共用，訊息必須寫清楚是給誰的**。
- 另一情境：現場主管平常用共用帳號報工，要簽核時才登自己帳號。
- 設定此綁定**不需要**另外開 RBAC 權限給員工。

## 1. 兩種綁定模式（語意務必分清）
| 模式 | 名稱 | 語意 | 通知走向 |
|---|---|---|---|
| `attach` | **綁定依附** | 員工原帳號**不需另外設權限、平常不登入**（帳密保留暫不取銷——使用者明示：未來可能用在「共用帳號上簽核時輸入本人密碼」；**不要**做成刪帳密） | 只送**共用帳號**（原帳號的站內 live_event_for_user 仍可寫一份留痕，供日後他登入回看） |
| `notify` | **開通** | 員工自有帳號照常使用（如現場主管），只是「也」用共用帳號 | **雙送**：原帳號＋共用帳號都收 |

另需：**共用帳號可設「不可改密碼」**（lock_password），避免現場有人隨手改掉害全廠登不進去。

## 2. 設定 UI 放哪（建議，非 createEvent.php）
- 使用者原本想放 `views/liveEvent/createEvent.php`（公告頁），**建議改放 `views/ADM/hr_settings.php` 新增一個「共用帳號管理」區塊**，理由：
  1. 這是「帳號/人事屬性」不是「單次公告的選項」，公告頁每次發文都會載入、不該塞管理功能；
  2. hr_settings 已有代理人設定等人事區塊，管理員動線一致；
  3. createEvent 頁已很擠。
- 區塊內容：
  - 左：共用帳號清單（`user.is_shared_account=1` 者）＋「把現有帳號標記為共用帳號」開關＋ lock_password 勾選。
  - 右：選定共用帳號後，其成員清單（姓名＋模式 attach/notify＋啟停），新增成員=從在職員工下拉多選（參照資料一律下拉，見 ai-rules/08）。
  - 僅管理員可操作（比照 hr_settings 現有權限判斷）。

## 3. Schema（sql.php 擋 ALTER/CREATE 之外的破壞性 DDL；ALTER 需用 PHP PDO 遷移腳本跑，範例見 roster 模組 scratchpad migrate 寫法）
```sql
-- user 表加欄（PHP PDO 遷移，先查 information_schema 防重跑）
ALTER TABLE user ADD COLUMN is_shared_account TINYINT NOT NULL DEFAULT 0;
ALTER TABLE user ADD COLUMN lock_password TINYINT NOT NULL DEFAULT 0;

CREATE TABLE shared_account_member (
  id INT AUTO_INCREMENT PRIMARY KEY,
  shared_uid INT NOT NULL,          -- 共用帳號 user.id（須 is_shared_account=1）
  member_uid INT NOT NULL,          -- 員工 user.id
  mode VARCHAR(10) NOT NULL DEFAULT 'attach',  -- attach=綁定依附 / notify=開通(雙送)
  active TINYINT NOT NULL DEFAULT 1,
  created_by INT NOT NULL DEFAULT 0,
  created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
  UNIQUE KEY uq_pair (shared_uid, member_uid),
  INDEX idx_member (member_uid)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;
```
- 一個員工可綁多個共用帳號嗎？→ 預設可（uq 是 pair），UI 上正常一人一廠一台。
- 共用帳號本身（state=90 公用帳號那批）與 is_shared_account 的關係：**不要**拿 state=90 當判斷（90 另有語意），一律用新欄位 is_shared_account。

## 4. 通知轉送（本案核心，改一處全站生效）
通知鏈：各模組 → `live_event`＋`live_event_target` → **`src/push/push_send.php` 的 `eg_push_event_recipients()`**（展開成 user id 收 Web Push）＋ `telegram/notify_event.php`（Telegram）＋ live_event_for_user（站內清單）。

**改造點＝收件人展開層，各模組（含輪值排班 roster_notify）零修改自動受益：**
1. 在 `src/common/` 新增共用函式（例 `shared_account_lib.php`）：
   - `eg_shared_fanout(PDO $db, array $uids): array` → 輸入原收件人，回傳 `[['deliver_uid'=>共用或本人id, 'for_uid'=>員工id, 'for_name'=>員工姓名], ...]`：
     - 無綁定者：deliver=本人。
     - `attach`：deliver=共用帳號（本人不推播；live_event_for_user 仍寫本人一份留痕）。
     - `notify`：deliver=本人＋共用帳號兩筆。
     - 同一共用帳號多位成員同時是收件人 → **每位成員各一則**（各自前綴姓名），不要合併成一則（才能分辨給誰）。
2. `push_send.php`：推播 payload 的 title 前綴 **「【給 ○○○】」**（for_uid≠deliver_uid 時才加）。
3. `telegram/notify_event.php`：同樣前綴。
4. 站內清單（live_event_for_user 產生處，grep `live_event_for_user` INSERT）：共用帳號也要寫一筆並在顯示時帶「給 ○○○」標籤——顯示端在 `views/liveEvent/`（清單頁）與側欄鈴鐺，需把 for_name 存起來（live_event_for_user 加欄 `for_uid INT NULL`，顯示時 JOIN user 取名）。
5. **去重**：attach 模式別讓本人又推播又收共用（本人不推播）；同一 event 同一 deliver_uid 同一 for_uid 只一則。

## 5. 不可改密碼（lock_password）
- grep 全站改密碼端點（關鍵字 `password`、`pwd`、`UPDATE user SET.*pass`），在每個改密碼入口加：目標帳號 `lock_password=1` → 擋下並提示「此帳號已鎖定密碼，請洽管理員」。
- hr_settings 共用帳號區塊可切 lock_password；共用帳號建立/標記時**預設鎖定**。
- 管理員後台改密碼（若有）可豁免，但要留 audit（比照 audit_log rbac_* 寫法，見記憶 audit_log_module）。

## 6. RBAC / 權限
- 綁定管理：僅管理員（hr_settings 既有權限）。
- `attach` 成員**不需**任何 RBAC 角色（他用共用帳號的權限做事）；`notify` 成員維持自己原有角色。
- 共用帳號本身的 RBAC 角色照常設定（它是實際登入的操作者）。

## 7. 驗收清單（做完逐項驗）
- [ ] hr_settings 可標記共用帳號、鎖密碼、增刪成員、切 attach/notify。
- [ ] 發一則指定「員工A（attach 綁在共用X）」的通知：X 的推播/Telegram/站內都收到且標「【給 A】」；A 本人不推播、站內留痕。
- [ ] 員工B（notify 綁在共用X）：B 與 X 都收到；X 那則標「【給 B】」。
- [ ] 同一則通知同時給 A、B：X 收到兩則，各自前綴。
- [ ] 未綁定者行為完全不變（回歸測試：公告、QA、報價、輪值排班 ROSTER 通知）。
- [ ] lock_password=1 的帳號改密碼被擋。
- [ ] 測試資料清理照 testing_discipline（只刪自己建的列；`__xxx__` 命名不發真實推播）。
- [ ] 鐵律6 收尾：php -l、每檔 commit＋`git pushall`、page_change_log。

## 8. 邊界/陷阱
- user 表有 latin1 欄位中文比對問題（見記憶 db_charset_constraints），新表一律 utf8mb4。
- `$_SESSION['id']` 才是登入者 id（見記憶 session_userid_key）。
- 推播失敗不得阻斷主流程（全部 try/catch 靜默，比照 bom_track_notify.php）。
- 別動 `vw_live_event`（廢棄空表）。
- 輪值排班的通知（ref_type='ROSTER'，src/common/roster_lib.php `roster_notify()`）已上線走同一條鏈——改收件人展開層時**務必回歸測試它**。
