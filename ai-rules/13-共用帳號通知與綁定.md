## 0. 背景與需求（使用者原話整理）
- 現場大多數員工用**共用帳號**登入（例如各廠區一台平板一個帳號），個人帳號幾乎不開。
- 通知（live_event → Web Push / Telegram / 站內清單）目前只送「員工本人帳號」→ 用共用帳號的人**收不到**。
- 需求：可設定「哪些員工使用哪個共用帳號」，通知該員工時自動轉送到共用帳號；**因多人共用，訊息必須寫清楚是給誰的**。
- 另一情境：現場主管平常用共用帳號報工，要簽核時才登自己帳號。
- 設定此綁定**不需要**另外開 RBAC 權限給員工。

## 1. 兩種綁定模式（語意務必分清）
| 模式 | 名稱 | 語意 | 通知走向 |
|---|---|---|---|
| `attach` | **綁定依附** | 員工原帳號**不需另外設權限、平常不登入**（帳密保留暫不取銷——使用者明示：未來可能用在「共用帳號上簽核時輸入本人密碼」；**不要**做成刪帳密） | 只送**共用帳號**（原帳號的站內 live_event_for_user 仍可寫一份留痕，供日後他登入回看） |
| `notify` | **開通** | 員工自有帳號照常使用（如現場主管），只是「也」用共用帳號 | **雙送**：原帳號＋共用帳號都收 |

另需：**共用帳號可設「不可改密碼」**（lock_password），避免現場有人隨手改掉害全廠登不進去。

## 2. 設定 UI 放哪（建議，非 createEvent.php）
- 使用者原本想放 `views/liveEvent/createEvent.php`（公告頁），**建議改放 `views/ADM/hr_settings.php` 新增一個「共用帳號管理」區塊**，理由：
  1. 這是「帳號/人事屬性」不是「單次公告的選項」，公告頁每次發文都會載入、不該塞管理功能；
  2. hr_settings 已有代理人設定等人事區塊，管理員動線一致；
  3. createEvent 頁已很擠。
- 區塊內容：
  - 左：共用帳號清單（`user.is_shared_account=1` 者）＋「把現有帳號標記為共用帳號」開關＋ lock_password 勾選。
  - 右：選定共用帳號後，其成員清單（姓名＋模式 attach/notify＋啟停），新增成員=從在職員工下拉多選（參照資料一律下拉，見 ai-rules/08）。
  - 僅管理員可操作（比照 hr_settings 現有權限判斷）。

## 3. Schema（sql.php 擋 ALTER/CREATE 之外的破壞性 DDL；ALTER 需用 PHP PDO 遷移腳本跑，範例見 roster 模組 scratchpad migrate 寫法）
```sql
-- user 表加欄（PHP PDO 遷移，先查 information_schema 防重跑）
ALTER TABLE user ADD COLUMN is_shared_account TINYINT NOT NULL DEFAULT 0;
ALTER TABLE user ADD COLUMN lock_password TINYINT NOT NULL DEFAULT 0;

CREATE TABLE shared_account_member (
  id INT AUTO_INCREMENT PRIMARY KEY,
  shared_uid INT NOT NULL,          -- 共用帳號 user.id（須 is_shared_account=1）
  member_uid INT NOT NULL,          -- 員工 user.id
  mode VARCHAR(10) NOT NULL DEFAULT 'attach',  -- attach=綁定依附 / notify=開通(雙送)
  active TINYINT NOT NULL DEFAULT 1,
  created_by INT NOT NULL DEFAULT 0,
  created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
  UNIQUE KEY uq_pair (shared_uid, member_uid),
  INDEX idx_member (member_uid)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;
```
- 一個員工可綁多個共用帳號嗎？→ 預設可（uq 是 pair），UI 上正常一人一廠一台。
- **`state=90` 與 `is_shared_account` 的分工（2026-07-29 定案，兩者都要用，別搞混）：**
  | 用途 | 判斷依據 |
  |---|---|
  | 「這個帳號是不是共用帳號」＝通知轉送、站內可見範圍、代簽、推播放行 | **一律 `is_shared_account = 1`**，不可用 state |
  | 「哪些帳號**可以被標記**為共用帳號」＝hr_settings 候選下拉 | `state = 90`（員工管理的「特殊帳號(不列入員工)」，使用者確認就是這個）**且** 名稱含「共用」或「公用」 |
  - 常數 `SA_CAND_WHERE`（`src/store/_shared_account_api.php`）是候選條件的唯一定義，前端下拉與後端 `set_shared` 共用同一條件。
  - **現場帳號實際叫「生管公用」「報工公用」（公用，不是共用）**，只比對「共用」會一筆都撈不到 → 兩種寫法都收。

## 4. 通知轉送（本案核心）

> **首版有三處假設是錯的，實作時已更正，後續維護請以本節為準：**
> 1. ~~改 `eg_push_event_recipients()` 就全站生效~~ → **錯**。roster / car / bom_track / leave / personal_task 五個模組自己組 `$userIds` 直接送，根本不經過它。真正的唯一收斂點是 **`eg_push_send_to_users()`**（連 `eg_push_event_notify()` 最後也是呼叫它），而且 payload 就在該函式內，才有辦法「每位成員各一則、各自加前綴」。
> 2. ~~Telegram 只有一處~~ → 主線在 `eg_telegram_event_notify()`；`personal_task_notify.php` 走 `tg_send_text()` 底層直發是第二處（已決定個人工作提醒**不轉送**，見下）。
> 3. ~~站內清單靠 `live_event_for_user` 寫入~~ → **錯**。該表是「已閱狀態表」不是收件匣。站內清單是**讀取當下**拿登入者身分去比對 `live_event_target`，所以要改的是讀取層的比對集合，不是加 `for_uid` 欄。

通知鏈：各模組 → `live_event`＋`live_event_target` → Web Push（`eg_push_send_to_users`）＋ Telegram（`eg_telegram_event_notify`）＋ 站內清單（讀取時比對）。

**實際改造點（各模組零修改自動受益）：**
1. `src/common/shared_account_lib.php`：
   - `eg_shared_fanout(PDO $db, array $uids, ?array $fanoutOnly = null): array` → 回傳 `[['deliver_uid'=>..,'for_uid'=>..,'for_name'=>..], ...]`
     - 無綁定者：deliver=本人（行為完全不變）。
     - `attach`：deliver=共用帳號（本人不推播；站內清單本人仍看得到）。
     - `notify`：deliver=本人＋共用帳號兩筆。
     - 同一共用帳號多位成員同時是收件人 → **每位成員各一則**，不合併（才分得出給誰）。
     - `$fanoutOnly`＝可轉送的 uid 白名單（＝指名收件人）；null＝全部可轉送。
   - `eg_shared_named_recipients()`／`eg_shared_view_uids()`／`eg_shared_member_names()`／`eg_shared_resolve_actor()`／`eg_shared_password_locked()`。
2. `eg_push_send_to_users($db, $uids, $payload, $opts)`：內部 fanout，轉送則 title 前綴 **「【給 ○○○】」**。
   - `$opts['event_id']` → 只轉送該公告的**指名**收件人（見第 4-1 點）。
   - `$opts['fanout' => false]` → 完全不轉送（私人內容，個人工作提醒即用此）。
   - **tag 必須帶 `-for{uid}`**：Web Push 同 tag 會互相覆蓋，否則多位成員只剩最後一則。
3. `eg_telegram_event_notify()`：同樣 fanout ＋前綴；轉送則**不附回簽/已閱按鈕**（見第 4-2 點）；以 `chat_id × for_uid` 去重（本人與共用帳號可能是同一支手機）。
4. 站內清單：`eg_shared_view_uids()` 把比對條件從 `target_id = 我` 擴成 `target_id IN (我, 我的成員…)`，顯示「給 ○○○」標籤；**未讀/完成狀態改看該成員本人**（共用帳號自己按不算數）。
5. **去重**：同一 deliver_uid × for_uid 只一則；attach 本人不推播。
6. `eg_push_active_user_filter()` 必須放行 `is_shared_account=1`：現場共用帳號多半是 `state=90`，原本會被這道過濾整批丟掉（不改＝整套做完仍然零推播）。

### 4-1. 只轉送「指名通知」（使用者定案）
`target_type='user'`（點名給某人的簽核/待辦/提醒）才轉送；`all`/`dept`/`status` 廣播不逐人轉送。
否則一台平板綁 5 個人，一則全體公告會變成 6 則，現場直接被洗版。

### 4-2. 已閱/回簽的身分（使用者定案：**須輸入本人密碼**）
共用帳號上按「已閱／回簽」若直接記成共用帳號，已讀名單與 AS9100 可追溯性都會失真。因此：
- 站內：跳「本人確認」窗要該員工密碼 → 驗過才寫，紀錄記在**員工本人**，並以 `signed_via`（= 共用帳號 id）留痕。
- Telegram：按鈕無法驗密碼 → 轉送則**不給按鈕**，改文字提示「請本人登入系統確認」。
- 已閱與回簽一致處理：不輸密碼就只是看得到，不寫任何紀錄。
- **未涵蓋**：QA / CAR / 報價等模組**自己的檢視頁**進頁會依 session 自動標已閱，共用帳號開啟成員的該類通知時仍會記成共用帳號。要補時各頁需自行接 `eg_shared_resolve_actor()`。

### 4-3. 隱私例外
個人工作紀錄提醒（`personal_task_notify.php`）僅本人可見，**不轉送**共用帳號（現場平板多人共用，會把私人待辦公開），以 `['fanout' => false]` 關閉。

## 5. 不可改密碼（lock_password）
全站改密碼入口共三處，已全部處理：
| 入口 | 處理 |
|---|---|
| `views/user/user.php`（本人改密碼） | `lock_password=1` → 擋下「此帳號已鎖定密碼，請洽管理員」 |
| `src/store/_setupUser.php`（舊入口） | 同上擋下。另：該檔原本 `WHERE id=$_GET[id]` 是字串內插，守門查的 id 與實際更新的 id 可能不同而形同虛設 → 已改為整數＋參數化（**這是讓守門生效的必要修正，不是重構**） |
| `src/store/_employee_api.php`（管理員） | **豁免可改**，但改到鎖定帳號時寫 `audit_log`（`action_type='pw_change_locked'`） |
- hr_settings 共用帳號區塊可切 lock_password；標記為共用帳號時**預設鎖定**。

## 6. RBAC / 權限
- 綁定管理：僅管理員（hr_settings 既有權限）。
- `attach` 成員**不需**任何 RBAC 角色（他用共用帳號的權限做事）；`notify` 成員維持自己原有角色。
- 共用帳號本身的 RBAC 角色照常設定（它是實際登入的操作者）。

## 8. 邊界/陷阱
- user 表有 latin1 欄位中文比對問題（見記憶 db_charset_constraints），新表一律 utf8mb4。
- `$_SESSION['id']` 才是登入者 id（見記憶 session_userid_key）。
- 推播失敗不得阻斷主流程（全部 try/catch 靜默，比照 bom_track_notify.php）。
- 別動 `vw_live_event`（廢棄空表）。
- 輪值排班的通知（ref_type='ROSTER'，src/common/roster_lib.php `roster_notify()`）已上線走同一條鏈——改收件人展開層時**務必回歸測試它**（跑 `ai-rules/tools/test_roster_notify_regression.php`）。
- **Web Push 的 `tag` 相同會互相覆蓋**：轉送多位成員時 tag 一定要帶 `for_uid`，否則現場只會看到最後一則。
- `eg_push_active_user_filter()` 的 `state IN (1,99)` 白名單是隱形殺手：共用帳號多為 `state=90`，忘了放行就整套失效且完全不報錯。
- 遷移未跑時，`shared_account_lib` 的所有函式會退化為「無綁定」，全站行為與改造前一致（`eg_shared_ready()` 把關），不會因為少跑遷移而壞掉。
- 測試腳本挑收件人時，請挑「無 push 訂閱且無 Telegram 綁定」的員工，才不會真的發出通知（`roster_notify` 的 `__` 防護只擋標題含 `__` 的情況）。
