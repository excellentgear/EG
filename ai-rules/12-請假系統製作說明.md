### 0.1 使用者已拍板的規則（勿再重問）
1. **不做假別額度表**；特休改用 `annual_leave_lib` 依到職日即時算，已用＝該年度 approved 特休 `total_days` 加總，超額送審擋下。
2. **粒度依假別各自設定**：`leave_type.unit_type` = hour / halfday / day。
3. **補請假**限 `leave_backdate_limit_days` 天內（預設 7），單上標記 `is_backdated`。
4. **撤回／銷假依請假日期分三種（2026-07-30 定案，`eg_leave_cancel_mode()`；管理者不受限）**：
   - **起日尚未到** → 可直接撤回／銷假，通知所有已簽核者與代理人。
   - **請假期間內（含請假當日）** → **撤回需主管簽核**：轉狀態 `cancel_pending`，原因必填，通知第一層主管（`mode=sign`）；核准才真撤除，駁回則回復原狀態。
   - **請假期間已結束** → **不開放自行撤回**，只能請管理員處理。理由：避免「已休假卻沒有請假紀錄」。
   - `cancel_pending` 期間視為假仍成立：不可改內容、仍佔用時段、仍計入特休送審中額度。
   - `leave_approval.approval_kind` 區分 `leave`（請假簽核）與 `cancel`（撤回簽核）；**寫任何請假簽核查詢都要限定 `kind='leave'`**，否則會把撤回簽核列誤當成請假的層級。
5. **兩張簽核表職責分開**：`leave_approval`＝流程狀態（送審時每層一次建好、逐層推進、OR-gate）；`leave_sign_record`＝只增不改簽章軌跡。**兩者同一 transaction 各寫各的，不互相推導**。
6. **代理人不參與簽核**：`leave_type.agent=1` 的意義是「此假別需要職務代理人」，**核准後才通知他接手**。`leave_sign_record.step_no=0` 保留不用。
   **代理人由系統自動解析，申請人不可挑選（2026-07-30 定案，勿改回下拉選單）**：
   - 人事設定（`user_delegate`）本來就有 `priority`，取**第一順位**；該順位若在申請人請假期間**自己也請假**（pending 或 approved 且時段重疊）就跳到**第二順位**，以此類推。
   - 申請人有**多個職務身分**（主職＋兼任）時，**每個身分各自解析一位**——請假是整個人不在，各身分的工作都要有人接，且各身分的代理設定常是不同人。
   - 某身分所有順位都不可用 → 記為「無可用代理人」並保留原因，**不擋請假**。
   - 解析入口 `eg_leave_resolve_agents()`；結果存 `leave_request_agent`（每身分一列，含用到第幾順位、被跳過者與原因）。`leave_request.agent_user_id` 只是相容用的單一欄位，**不是完整資料**。
7. **檢視範圍**：本人 / 主管看部門含下轄（職稱有 `position_level.level` 即視為主管）/ `leave_view_all` 或管理員看全部。
8. **頂層簽核**：主管鏈解析不到上一級時由 `leave_final_decider_id`（最終裁決者）補位。
9. **證明文件**：假別三欄驅動 `require_attachment` / `attach_min_days` / `allow_attach_later`；**待補證明不擋簽核**，單上標記 `attach_status='pending'`，可事後補件。
10. **行事曆**：原有休假事件與邏輯不動。送審即寫「請假申請中」事件（`event_category` 名稱查詢取 id，勿寫死）並顯示 `EGStamp.badge('pending')` 申請中章；核准時**同一筆**轉為「休假」(category_id=1) 並改為全體可見；退回/撤回/銷假只刪 `leave_request.evenement_id` 指到的那筆。可見度必須同時寫 `evenement_target` 與 `evenement_recipient_cache`，只寫 `evenement_actor` 事件不會出現在任何人的行事曆。

- **5 張表原本已存在但交易面未實作**（`leave_type` 有 6 筆假別，其餘全空），本次是在既有 schema 上補欄位與功能，非重開表。
- 假別設定已可用：`views/ADM/hr_settings.php` 的「假別設定」＋ `views/ADM/leave_management_api.php`（leave_type CRUD：`need_approval` 是否需主管簽、`agent`=需申請人代理人會簽、`max_approval_level` 要簽到第幾階 1~5）。
- 行事曆連動：`src/store/get_users_on_leave.php` 靠 `evenement` 的 `category_id=1(休假)` 判斷某日誰休假。**請假核准後必須寫一筆休假 evenement**，行事曆與該端點才看得到。
- **`leave_agent_setting` 是舊設計的「請假專用代理表」且為空 → 一律不要用它**（用它就違反下方鐵律1）。可視為已廢棄，勿讀勿寫。

## 1. 本系統鐵律（違反＝重做）
1. **代理一律走 `src/common/delegate_lib.php`，禁用 leave_agent_setting、禁自寫 user_delegate SQL**（見 [ai-rules/11]）。請假有兩處代理，都呼叫 `eg_resolve_signer()`：
   - (a) **申請人的代理人會簽**：`leave_type.agent=1` 時，step 0 需申請人的代理人簽；代理人＝對「申請人」解析出的代理。
   - (b) **主管不在由其代理簽**：某層主管當下請假/有行程 → 該層改由該主管的代理簽（對「該主管」呼叫 eg_resolve_signer，行程閘門＋SoD 迴避自動處理）。
2. **主管簽核鏈用職稱階級解析，不寫死人**：第 1..max 層的實際簽核人，用申請人部門/職稱＋`position_rank`(階級)＋`department` 樹＋`department_position.primary_user_id` 逐級往上找（同 `eg_resolve_supervisor` 邏輯，需要時擴充成「取上 N 級」的鏈）。
3. **核准後寫行事曆**：`leave_request` 轉 `approved` 時建立一筆 `evenement`（category=休假、actor=申請人、start/end=請假時段）。delegate_lib 的行程閘門會據此/`leave_request(approved)` 自動讓當事人「今日不在→代理生效」。
4. **附件走 temp/active 暫存狀態機**（診斷證明等）：新增單就能上傳、DB 只存檔名/相對值、絕不寫死絕對路徑（鐵律5、[ai-rules/07]）。
5. **通知走 `live_event`（ref_type='LEAVE'）**：順路觸發、勿洗版；測試單命名 `__xxx__` 不發真實推播（見記憶 testing_discipline）。

## 2. 狀態機與資料表分工
- `leave_request.status`：`pending`(送審) → `approved` / `rejected` / `canceled`。
- 送審後鎖定內容不可改；撤回＝`canceled`（限 pending，或最後決行前）。
- **兩張簽核表的語意要先切清楚，別雙寫不一致**（動工前跟使用者確認）：
  - `leave_sign_record`：逐步簽章軌跡（step_no 0=代理人會簽、1~5=各層主管），建議作為**統一簽章軌跡**。
  - `leave_approval`：每層決行結果（approval_level 應簽層級、approver_level 實際簽核者層級、approver_id、`delegate_id`=若由代理簽、status、remark）。
- **OR-gate/收回**：同層可簽者（主管本人或其代理）任一簽即該層完成，其餘待辦自動收回（比照報價/QA，見記憶 order_change_policy / qa_abnormal_notify）。

## 3. 簽核流程（組裝順序）
1. 送審 → 若 `leave_type.agent=1`：step0 申請人代理人會簽（`eg_resolve_signer(applicant, {flow_key:'leave'})`）。
2. 逐層主管 1..`max_approval_level`：每層 target=該層主管（由階級鏈解析）→ `eg_resolve_signer(target, ctx)` 得實際簽核人（主管在→本人；不在→其代理；代理＝申請人→SoD 直升上一級）。
3. 全通過 → `approved`：寫休假 `evenement`、發 `live_event` 通知申請人＋代理人＋相關人、（若有假別額度表）扣額度。
4. 任一層 `rejected` → 整單 rejected、通知申請人。

## 4. 與代理系統的接點（務必照 [ai-rules/11]）
- 解析簽核人唯一入口：`eg_resolve_signer($db,$targetUserId,$ctx)`，`ctx.flow_key='leave'`、`applicant_id`=申請人、scope 帶該主管的部門×職稱身分。
- 判斷某人今日在不在：`eg_user_busy_today()`。主管鏈：`eg_resolve_supervisor()`（必要時擴充多級）。
- **別在請假頁另做代理設定 UI**；代理設定一律回 hr_settings。

## 5. UI／權限（比照全站，見 [ai-rules/08]、[ai-rules/10]）
- 申請頁：日期/時間**可點月曆**；假別下拉；原因；附件即時上傳；顯示「將由誰簽核」預覽（呼叫解析後列出）。
- 簽核頁：本人待簽清單；用 `eg_stamp.js` 蓋章＋押簽核日期；限本人或其代理。
- 列表 >10 分頁、分頁鈕右上、每頁 5/10/20/50、PDF+CSV 匯出；**一律暖色系**、狀態燈號用固定色語意＋文字標籤（顏色非唯一資訊）。
- RBAC 每頁新增/修改/刪除/檢閱分開設；標頭顯示角色＋`?` 說明。
- 新頁**登記進選單**（`system_module_pages` INSERT＋綁「測試功能」主項目）＋`user_permissions` 加角色設定區塊（鐵律6）。

## 6.5 請假統計（2026-07-31 新增，第四個分頁）
- 入口：`views/ADM/leave_request.php` 的「📊 請假統計」分頁，子分頁＝月度／年度比較／趨勢／部門・人員。
- 後端 `eg_leave_stats()`（`leave_stats_lib.php`）＋ API `stats` / `stats_options`。
- **檢視範圍與請假單列表同一套**：人事(`leave_view_all`)/管理員看全公司；主管（主職職稱有 `position_level.level`）看自己部門含下轄；其他人整個分頁不出現。主管硬帶別部門的 `dept_id` 會被忽略（API 內驗）。
- **一次撈全部符合條件的單，再於 PHP 端彙總成各切法**，不下 6 支 GROUP BY。理由：月報／年報／趨勢／部門／人員是同一批資料的不同切法，分開下 SQL 一旦條件寫歪就會出現「月報加總 ≠ 年報」。測試裡有 6 項專門驗這件事。
- **年度／月份歸屬一律以請假起日計**（與 `eg_leave_year_usage()`、特休額度同口徑）。跨月長假整筆算在起日那個月，**不做逐日攤分**——攤分會把「這個月誰請假」變成「這個月有人在放假」，人事看的是前者。
- 留職停薪／育嬰留停天數極大會壓過其他假別，因此畫面一定要留**假別篩選**讓人事排除（色塊 chip，點一下切換）。
- 假別顏色走 `eg_leave_type_colors()` 固定暖色盤（見 [ai-rules/10]），**禁止各頁自己配色**。
- 統計用的人員資料走 `eg_leave_stats_people()` 而**非** `eg_people_list()`：統計看的是歷史事實，離職者去年請的假仍要算，濾掉會讓年度總計對不起來；但**篩選用的部門／人員下拉仍走 `people_list`**（人員列表鐵則）。
- 測試：`ai-rules/tools/test_leave_stats.php`（52 項）。
