# 26. 頁面管理員角色（本頁管理員＝全站超級管理員在「這一頁」的同權替身）

> 2026-10-05 制定，使用者明確要求全站適用。起因：合約訂單審查表（`con_review.php`）與產品開發評估表
> （`td_dev_eval.php`）都有「管理員可以不需送出、自動全部填寫並代為簽核」這種補資料/快速設定功能，
> 原本兩個模組都把它寫死限定**全站超級管理員**（`isAdmin`：`user_status in (9,90)` 或 `uid===1`）才能用，
> 連該模組自己早就建好的模組管理員角色（`con_review_admin`／`td_dev_eval_admin`）都不算數。使用者原話：
> 「除了全站管理員以外，可以增加本頁管理員角色嗎？只有本頁可以使用管理員權限（自動代簽這些）」——
> 要的不是另外再設計一套新角色，是把**既有的模組管理員角色，在這一頁的權力拉到跟全站超級管理員一樣**。

## 適用情境

任何模組只要有下列任一種「管理員才能用的特殊功能」，就要讓**本模組的管理員角色**也能用，不可以只留給
全站超級管理員：
- 自動/快速簽核（如「自動填寫並簽核」「全部自動簽核(指定日期)」）
- 補登歷史資料、整批修改已鎖定狀態的表頭/欄位
- 代替他人完成決行/核准/簽核這類原本該由特定人員做的動作
- 刪除已完成/已結案的正式紀錄
- 其他任何「不受正常流程狀態限制」的管理操作

## 兩層模型（本來就存在，不必另外新建）

每個模組的 `*_perms()` 函式本來就會回傳兩個旗標，差別只在於**後續各處要查哪一個**：

```php
$isAdmin  = 全站超級管理員（user_status in (9,90) 或 uid===1，或持有 is_system=1 的全站 admin 角色）
$canAdmin = $isAdmin || 持有本模組自己的 <module>_admin 角色（例：con_review_admin／td_dev_eval_admin）
```

**規則：模組內所有「管理員才能用的特殊功能」一律查 `canAdmin`，不要查 `isAdmin`。**
`isAdmin` 只留給**跨模組、非本頁事務**的場合使用（例如「身分：管理者」這種畫面標籤要特別標出來是全站
超級管理員、或者真的有不屬於任何單一模組的全站層級操作），本頁內部的一切管理行為都不該卡在 `isAdmin`。

## 落地做法

1. **模組的 `*_ensure_schema()`（或類似的角色自動建立邏輯）本來就要建好 `<module>_admin` 這個角色**
   （既有慣例，見 `con_review_lib.php`／`td_dev_eval_lib.php`／`equip_list_lib.php` 等模組），不必為了
   這條規則另外新建角色——`<module>_admin` 本身就是「本頁管理員」。
2. **API 層**：所有 `case` 分支裡判斷「這個人能不能用管理員功能」的地方，一律用 `$perms['canAdmin']`，
   不要用 `$perms['isAdmin']`。把這兩個混用是最容易犯的錯——常見症狀是「指派了模組管理員角色給某人，
   他卻還是打不開管理員專用的按鈕/功能」，因為某幾支 API 動作當初隨手寫成查 `isAdmin`。
3. **後端函式內部的 bool 參數**：像 `cnrv_decide($db,...,bool $isAdmin)`、
   `td_dev_eval_answer_filter_writable($db,...,bool $isAdmin,...)` 這種把「能不能繞過正常規則」當參數
   傳進去的函式，呼叫端一律傳 `$perms['canAdmin']` 的值（參數名稱仍可以留 `$isAdmin` 或改成更準確的
   `$isAdmin`／`$bypass`，重點是傳進去的**值**要對，不是參數名稱）。
4. **前端**：PHP 端輸出的管理員專屬按鈕/面板（`style="<?= $perms['canAdmin']?'':'display:none;' ?>"`）與
   JS 變數（例：`CAN_ADMIN`）全部改用 `canAdmin`；原本另外宣告一個 `IS_SUPER_ADMIN`／`isAdmin` 給 JS 用
   的，直接刪掉改用 `CAN_ADMIN`，不要保留兩套並存（兩套並存遲早有一處漏改）。
5. **畫面上的身分標籤仍可以分開顯示**（例：`$perms['isAdmin'] ? '管理者' : ($perms['canAdmin'] ? '○○管理員' : ...)`）
   ——這只是「讓使用者知道自己是哪一種管理員」的顯示文字，跟第 2～4 點的**權限判斷**是两件事，不要混淆：
   顯示文字可以誠實區分身分，但背後的**權力**要一樣大。

## 「代為簽核」時記錄要記真人，不是記操作者本人

本頁管理員（或全站超級管理員）用自動/快速功能代替他人簽核時，一律沿用 `ai-rules/19`／`ai-rules/24` 既有
的人員解析規則，把**真正該簽的那個人**記成簽核人，操作者本人只留進 proxy 欄位供稽核查核（參考實作：
`con_review_lib.php` 的 `cnrv_decide()`／`cnrv_approve()`，`con_review_doc.sales_decided_is_proxy`／
`sales_decided_proxy_uid`／`sales_decided_proxy_name` 等欄位）——**不可以不分青紅皂白一律記「操作者
本人」**，那會讓一般使用者看到一堆「超級管理員」或「某位本頁管理員」簽滿整張表單的荒謬紀錄。

## 已落地的模組

| 模組 | 本頁管理員角色 | 已改用 canAdmin 的功能 |
|---|---|---|
| 合約訂單審查表 `con_review.php` | `con_review_admin` | 自動填寫並簽核、刪除、item_save 整批改、dept_sign/decide/approve 代簽真人解析 |
| 產品開發評估表 `td_dev_eval.php` | `td_dev_eval_admin` | 全部自動簽核(指定日期)、32項快速設定、開啟全表填寫模式、表頭整批修改 |

新模組只要有「使用者明確要求管理員可以自動/代為做某件事」的功能，一律照這篇辦，不必每次重新問使用者
要不要加本頁管理員角色——**預設就要加**，除非使用者特別說這個功能只能全站超級管理員用（罕見，要問清楚）。
