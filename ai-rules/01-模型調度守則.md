# 模型調度守則
> 讀者：本專案的主對話 AI（任何等級）。目的：省 token、少出錯、可驗證。
> 本檔所有工具名與參數都對照過本環境實際 schema（2026-07-06），不是憑印象寫的。

## 0. 本環境實際可用的東西（先讀這段，不要憑印象）
- **Agent 工具**：參數 `subagent_type`、`model`、`prompt`、`run_in_background`、`isolation`。
  - `model` 可填：`sonnet`、`opus`、`haiku`（`fable` 僅特殊 session 有，日常不要指定它，失敗就換 `opus`）。
  - **Agent 工具沒有 effort 參數**，不要嘗試傳入。
  - 可用 `subagent_type`：`Explore`（唯讀搜尋）、`general-purpose`（可改檔的萬用）、`Plan`（唯讀規劃）、`claude`（同 general-purpose 的萬用）、`claude-code-guide`（問 Claude Code 本身的用法）。清單以你當下 session 的系統提示為準。
- **SendMessage**：可對「已存在的 subagent」追問，沿用它的 context；同一調查的追問用這個，不要重開新 agent。
- **多 agent 編排工具（若你的 harness 有 Workflow 之類的工具）**：**只有使用者明說要用（例如講「用 workflow」或「ultracode」）才可以呼叫**，平常禁用。沒有這類工具就直接用 Agent 並行派工。
- 主對話自己的模型由使用者用 /model 決定，AI 不能也不該自行更換主模型；要更強的腦，用 subagent 的 `model: 'opus'`。

## 1. 指揮官不下場
主對話（=指揮官）的 context 是全 session 最貴的資源，只放結論與決策。

**必須派 subagent 的工作**：
- 掃 repo / 跨多檔搜尋 / 「找出所有用到 X 的地方」
- 讀任何超過 2000 行的檔案來理解邏輯（本專案巨檔極多）
- 查網頁、讀外部文件
- 批次修改 3 個檔案以上的同型修改
- 驗收（見第 5 節）

**主對話自己做的工作**：
- 讀單一小檔的目標區段（Grep 定位後 Read ±100 行）
- 實際下 Edit、跑指令、跑 sql.php
- 與使用者對話、做決策

## 2. 派工三件套（缺一不可）
每個派工 prompt 必含：
1. **目標與動機**：要達成什麼、為什麼（讓 agent 遇到岔路能自己判斷）。
2. **驗收條件**：什麼樣算完成，可客觀檢查（例：「列出所有呼叫點的 檔案:行號，並確認無遺漏——用兩種不同關鍵字交叉搜尋」）。
3. **回報格式**：規定只回什麼（見第 3 節回報合約）。
現成模板見 [03-派工模板.md](03-派工模板.md)，直接填空使用。

## 3. 回報合約
- Subagent 只回：**結論 + 檔案:行號 + 必要的 10 行內關鍵引文**。
- 禁止回貼大段程式碼或檔案全文。長產物（報告、清單、diff）由 agent 自己 Write 落檔到 `ai-rules/work/`（或 scratchpad），只回傳路徑。
- 派工 prompt 裡要明寫這條，因為 agent 預設會把讀到的東西倒回來。

## 4. 選型表與升降級路徑

| 任務 | subagent_type | model |
|---|---|---|
| 機械式定位（找檔案、找字串、確認存在） | Explore | haiku |
| 語意搜尋（找「處理出庫邏輯的地方」） | Explore | sonnet |
| 一般實作 / 修 bug / 批次套用已知模式 | general-purpose | sonnet |
| 跨模組設計、難 bug、規劃 | Plan 或 general-purpose | opus |
| 驗收 / 審查（fresh context） | general-purpose | 與被驗對象同級或高一級 |

**升級規則**：
- haiku 錯 1 次 → 直接升 sonnet（不要跟 haiku 來回修）。
- sonnet 在**同一子任務**連錯 2 次 → 升 opus，且 prompt 必須附上完整失敗軌跡（做了什麼、錯誤訊息原文、已排除的假設），不是只丟原題。
- 同一件事最多重試 2 輪；第 2 輪仍失敗 → 停下來，把失敗軌跡整理給使用者，不要第 3 輪。

**降級規則**：
- opus/主對話解出「模式」後（例：確認了某類頁面的修改樣板），把模式寫成具體步驟，交給 sonnet（甚至 haiku）批次套用到其餘檔案。派工時附上一個已完成的範例 diff 作為樣板。

## 5. 驗證不自驗
寫程式的人不能當自己的驗收官。規則：
- **檔案落地** → read-back：開 fresh agent（或至少主對話重新 Read）確認檔案存在、內容完整、非截斷。
- **程式碼** → 可執行驗證優先：`php -l` 必做；有辦法實跑就實跑（curl 打頁面、sql.php 查結果）；不能只靠「看起來對」。
- **高風險判斷**（動到庫存數量、金額、權限、跨表交易） → 第二意見：開一個 fresh general-purpose agent，只給它需求與 diff，要它獨立判斷「這個修改會不會破壞既有行為」，不要告訴它你的結論。
- 驗收 agent 的 prompt 開頭寫明：「你是驗收者，你的價值在於找到問題。找不到問題也要說明你檢查了哪些點。」

## 6. Token 節約守則
- 同一個調查的第二個問題 → SendMessage 給原 agent，不要重開。
- 兩個互不依賴的搜尋 → 同一則訊息裡並行派兩個 agent。
- 派工 prompt 附上你已知的定位資訊（檔名、行號、關鍵字），別讓 agent 從零掃起。
