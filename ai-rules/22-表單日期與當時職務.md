# 表單一律以「業務日期當時」為準：職務、在職狀態、簽核人

> 最後修改：2026-09-16 — 新增**第 5 坑「下拉選單的候選清單也算解析人」**與共用庫 `eg_people_posts_asof()`，並讓 `check_asof_position.php` 多掃一個 C 區把這一類自動抓出來。起因：使用者回報「在別的頁面處理完這種狀況後，這邊還是出現一樣的問題，沒辦法寫進 MD 內自動改善與避免嗎?」——前四坑講的都是「系統自己找人」，**讓人手動挑的那個下拉一直不在規範裡**，所以每個新模組都會再犯一次。
> 建立：2026-08-19 — 起因：表單簽核設計器實測發現，業務日期 2025-11-28 的案件把「2025-12-09 才兼任品管部課長」的人解析成當時的主管並蓋章。使用者要求**全站表單都要注意日期與當時職務、在職人員**。

## 一句話規則

**任何表單要「解析人」或「顯示人的部門／職稱」時，基準日期一律是那張單據自己的業務日期，不是今天。**

補 2023 年的舊表單，就要用 2023 年的組織；當年是倉管組長、現在升課長，舊表單仍要印倉管組長。這跟 `ai-rules/16` 第三之四節「版次要依業務日期回推」是同一個原則的不同面向。

## 適用範圍（三件事都要）

1. **自動解析簽核人**：部門主管、上一階主管、部門負責人等，要用**當時**的部門與職級去找，不是現在的組織圖。
2. **顯示/列印的部門與職稱**：圖章上的 `{部門}{職稱}`、簽核欄的職稱、報表上的單位，要印**當時**的。
3. **挑人清單**：讓使用者手選人員時，標籤要顯示**業務日期當時**的部門職稱；否則補舊表單時照現職挑，很容易挑錯人。**主職與兼任要拆成各自的選項**，而且選到的是「人＋部門」不是只有人——因為**填表人是以哪個部門的身分填這張表，決定了「上一階主管」往哪個部門找**（高志宏以技術部工程師身分填→技術部往上；以品管部課長身分填→品管部往上，結果完全不同）。只顯示主職會看不出他還兼著課長，只選到「人」則根本無法決定簽核路線。單據要一起存下選定的部門（參考 `fsd_case.filler_dept_id`）。圖章上則相反，只印「他以什麼身分簽這張表」那一個職稱。

| 要問什麼 | 用什麼 | 在哪 |

## 四個必踩的坑（都是實際踩過的）

### 1. 回推不到人時，**不可以退回「現況」解析器**
這是最容易犯、也最難發現的一個。`eg_resolve_supervisor()`／`eg_org_dept_manager()` 都只看現在的組織，拿它們當 fallback 會**正好抵銷回推的意義**——2026-08-19 實測就是這樣把「現在才上任的課長」蓋到 2025-11-28 的文件上。

**做法**：業務日期在**過去**時，回推不到人就是「當時真的沒有這個角色」，該關解析不到人即可。寧可少一個章，也不要蓋錯人（錯的章在已完成文件上是簽章不實）。業務日期是今日／未來的單據才保留現況退回鏈。

### 2. 兼任常常才是簽核身分，不能只取「主職」
例：主職「技術部／工程師」、兼任「品管部／課長」，他是以課長身分簽核的。取職務時要**取職級最高的那一筆**（`position_level.level` 越小越高階），平手才用主職。

### 3. 「部門指定負責人」也要驗當時是否真的在那個部門
`department_position.primary_user_id` 是現況設定。把它納入回推鏈時，必須再用當日快照確認他當時確實隸屬該部門，否則又繞回同一個錯誤。

### 4. 在職狀態的判定要看「當時」，不是現在
**業務日期在過去的單據，要放行已離職者**——當年他在職，事後離職不該讓舊表單解析不到人／印不出章。業務日期是今日或未來的單據才要求在職。（同口徑：`as_document_management.php` 的 AS 負責人任期回推、`form_signer` 補案件的人員候選。）
特殊帳號（`user.state=90`）任何情況都排除。在職判定欄位是 `user.state`，不是 `user_status`（見 `ai-rules/08` 第五節）。

### 5.（2026-09-16 新增，這一坑已經在不同模組各踩一次）**下拉選單的候選清單也算「解析人」**
使用者 2026-09-16 的原話：「我發現在別的頁面處理完這種狀況後，這邊還是出現一樣的問題，沒辦法寫進 MD 內自動改善與避免嗎?」

**為什麼會一再重犯**：前四坑講的都是「系統自己去找人」，但**讓使用者手動挑人的那個下拉**同樣是解析人——
而它一律呼叫 `eg_people_list()` / `eg_people_posts()`，這兩支**永遠只回今天在職的人、今天的職稱**。
於是補歷史單據時：

- 當時在職、現在已離職的人**一個都挑不到**（例：文管中心負責人葉卿雅在 2025-11-03／2025-12-04 都還在職，補那兩張單卻選不到她）；
- 挑得到的人，**職稱印的是現在的**（當時是工程師、現在兼了組長，舊單就會印組長）；
- 更糟的是**完全不報錯**：畫面上就只是「這個人不在清單裡」，看起來像資料沒建好，不像 bug。

**做法**：任何有業務日期的模組，挑人清單一律改呼叫 `eg_people_list_asof()` / `eg_people_posts_asof()`，
並且**存檔時後端要用同一個業務日期再解析一次**（鐵律8）——只改前端的話，使用者挑得到卻存不進去，而且看不出原因。
「業務日期」要用**這張單真正的那個日期**（稽核通知單＝稽核起日、查檢表＝稽核日期、製表人＝製表日期），
日期欄位一改，清單要跟著重抓（不重抓的話畫面上還是舊日期那批人）。

**唯一實作**：`eg_people_posts_asof()` 在 `src/common/people_lib.php`。**不要再各模組自己寫一份**——
`doc_apply_lib.php` 就曾自己寫了一支 `da_people_posts_asof()`，結果內部稽核完全不知道它的存在又踩一次同樣的坑
（現在該支已改成薄包裝轉呼叫共用庫）。

**怎麼擋住下一次**：收尾的 `check_asof_position.php` 已新增 **C 區**，自動列出
「有業務日期、卻只呼叫 `eg_people_list()`／`eg_people_posts()`（沒有 `*_asof`）」的檔案。
C 區是**嫌疑名單不是錯誤清單**：清單本來就只給「今天」用的頁面（現場簽到、即時通知對象、今天要派工的人）不必改。

### 6.（2026-09-16 新增）**回推的是「職務」，不是「名稱」——名稱一律用 id 回查現名**
`user_position_history` 的 `before_json`／`after_json` 會把**當時的名稱**跟 id 一起凍結存進快照
（`{"department_id":1,"department_name":"技術部",...}`）。部門後來由「技術部」改名「技術課」，
快照裡仍是舊名，於是畫面印出一個 `department` 表裡根本不存在的單位。

**改名不是改組織**：同一個 `department_id` 就是同一個單位，要印**現在的名字**；
只有那個 id 真的被刪掉了，才退回快照裡的舊名（至少還看得懂那是誰）。
職稱（`position`）同理。

**這一坑最難發現的地方：它不是只有補舊資料才會發生。** 只要那個人有**任何一筆**職務異動紀錄，
`eg_position_snapshot_at()` 對**今天**的日期也是回傳該筆紀錄的 `after_json`＝凍結的舊名。
所以「今年新建的單據應該是對的」這個直覺是錯的——2026-08／09 才建立的會議紀錄一樣存著「技術部」。
（`Meeting_API.php` 寫入 `meeting_attendee.dept_name` 用的就是 `eg_people_list_asof()`。）

已修正並必須保持一致的三支：`eg_people_list_asof()`／`eg_people_posts_asof()`（`people_lib.php`）、
`ia_identity_asof()`（`internal_audit_lib.php`，另有 `ia_dept_name_now()`／`ia_position_name_now()`）。
**自己另外讀快照 JSON 的地方要比照辦理**，不要直接用 `$snap['department_name']`。

> 已存進資料表的顯示值（如 `meeting_attendee.dept_name`）是寫入當下就固定的文字，
> 修了函式不會回頭改舊資料；那些表通常也沒存 dept_id 可以安全回推，**不要擅自批次改寫使用者的歷史紀錄**，
> 需要時先列出逐列新舊對照請使用者確認。

## 不要做的事

- **不要修改 `eg_resolve_supervisor()` / `eg_org_dept_manager()` 本身**加日期參數：請假、採購、簽核鏈都在用，改了要全面回歸測試（鐵律4）。在自己模組加日期版查找即可。
- 不要自己解讀 `user_position_history` 的 `before_json`／`after_json`，一律走 `position_history_lib.php`。

## 收尾驗收

```
& C:\MAMP\bin\php\php8.3.1\php.exe C:\MAMP\htdocs\EGsystem\ai-rules\tools\check_asof_position.php
```
掃出「有業務日期欄位、又在解析人員／顯示職稱，但沒有用日期版查找」的模組，列成待檢清單。輸出三區：

- **A**＝會用現況解析器（`eg_org_dept_manager`／`eg_resolve_supervisor`／`eg_org_user`）卻沒有任何回推痕跡
- **B**＝已有回推痕跡（僅供參考，四個坑仍要人工確認）
- **C**＝**挑人清單只用現況**（`eg_people_list`／`eg_people_posts`，沒有 `*_asof`）＝第 5 坑

**這支工具只能提示嫌疑點，不能證明正確**——真正的驗收是：拿一個有補登過職務異動的人（或一個已離職的人），用他異動前後／離職前後的日期各建一張單，確認**挑得到的人**與**印出來的職稱**都會跟著變。
