# 24. 審核層級規範（「單位主管」要追溯到哪一層）

> 2026-09-16 制定，使用者明確要求全站適用。起因：文件制、修申請單（`views/ADM/doc_apply.php`）自動簽核時，
> **品管組 組長 蔣騏竹自己開的單，「單位主管」欄蓋的是他自己的章**。使用者指出組織圖上他上面還有品管課課長，
> 「單位主管應該要追朔到上級單位的主管簽章才對」，並補充：**直線單位最高為「課」**，課級部門內的最高主管
> 就是申請人本人時，單位主管可從缺、由申請人自己簽，**不會再往上追到課級以上（廠長／總經理）**。
> 使用者同時指出「其他的單據也有相同問題」，故本篇是**全站通則**，不是某一頁的特例。
>
> 唯一實作：`src/common/unit_supervisor_lib.php`（`eg_unit_supervisor()`）。
> 組織資料來源：`department`（`parent_id`／`level`，設定入口 `views/ADM/department_job_title_settings.php`
> 的「上層部門」與「層級」）＋`position_level.level`（設定入口「部門與職稱設定 → 職稱階級管理」）。

## 一、規則本文（三條）

1. **單位主管＝申請人所屬單位的「最高主管」**（該單位職級最高的那一位；職級＝`position_level.level`，數字小＝高）。
2. **申請人自己就是該單位最高主管 → 往上一層單位**（`department.parent_id`）取該單位的最高主管，逐層往上。
   例：品管組 組長開單 → 往上一層 = 品管課 → 課長；生管組 組長開單 → 資材課 → 副理。
3. **天花板＝「課」級**（`department.level <= 3`）。課級以上（總經理室／董事長室）是**所有單位的共同上級**，
   不是誰的單位主管，所以：
   - **課級單位內的最高主管就是申請人本人時，單位主管從缺**（`vacant=true`、`is_top=true`）；
   - 從缺時**怎麼處理由各模組自己決定**（見第三節），但一律**不可以**再往上追到廠長／總經理當「單位主管」。

`department.level` 的語意（欄位註解，勿改）：`1`=董事長室、`2`=總經理室、`3`=部門／課室、`4`=組別、`5`=小組。
天花板值寫在常數 `EG_UNIT_SUP_TOP_LEVEL`（=3），需要時可用 `eg_unit_supervisor(..., ['top_level'=>n])` 覆寫。

### 判定細節（已在共用庫處理，呼叫端不要自己再算一次）

- **同一單位內誰是「最高主管」**：`level` 升冪 → 職稱 `sort_order` 升冪（課長先於副課長、組長先於副組長）
  → 該部門×職稱的**指定負責人**（`department_position.primary_user_id`）優先 → 主職優先 → id。
  所以副組長的單位主管是**同組的組長**，不會跳過他直接找課長。
- **兼任**：一定要把「以哪個單位的身分申請」傳進 `$deptId`。兼任者的主職可能是沒有職級的工程師，
  拿主職職級去比另一個單位的人會判錯（舊版 `eg_resolve_supervisor()` 就是這樣把同組的副組長判成組長的上級）。
- **業務日期**：有業務日期的單據一律把 `$asof` 傳進來，共用庫會依 ai-rules/22 回推**當時**的部門／職稱／在職狀態。
- **留職停薪／育嬰留停（`user.state` 2、3）不列入**主管候選——人不在，單子會卡住；他的下屬依規則往上一層取。
- **代理**不在這一層處理：解析出「該誰簽」之後，呼叫端一律再過 `delegate_lib` 的 `eg_resolve_signer()`（ai-rules/11）。

## 二、怎麼用（禁止各頁自刻）

```php
require_once __DIR__ . '/unit_supervisor_lib.php';

$sup = eg_unit_supervisor($db, $applicantId, $applyDeptId, $bizDate);   // $bizDate 空字串＝現況
if (!empty($sup['id'])) {
    // $sup['id'] / ['name'] / ['dept_name'] / ['position_name'] / ['hops'] / ['reason']
} else {
    // 從缺：$sup['is_top']=true 代表申請人就是課級單位的最高主管（正常情況，不是錯誤）
}
```

只要 user id 時用 `eg_unit_supervisor_id()`；只要「某單位的主管是誰」（與申請人無關，例如核發／回收簽收欄、
受稽單位主管）請用 `eg_unit_dept_head()` 或既有的 `eg_org_dept_manager()`，**那不是本規則的適用情境**。

## 三、從缺時各模組怎麼處理（使用者已定調，勿自行更動）

| 情境 | 從缺時的處理 | 為什麼 |
|---|---|---|
| **簽章欄**（文件制修申請單四格簽章） | **蓋申請人自己的章** | 紙本上這一格本來就是申請單位自己蓋；使用者明確要求不做權責迴避、不留白 |
| **簽核關卡**（工程變更申請單「單位主管」關） | 這一關略過，簽章欄留白由紙本手蓋 | 沒有人可簽，不可讓單子卡死 |
| **核准關卡**（公出單） | 改由**最高核准人員**核准 | 紙本附註本來就這樣寫（主管公出請總經理核准）；核准一定要有人做，不能從缺 |
| **教育訓練需求申請單** | 視同免審、系統自動核准 | 原本行為，維持不變 |

## 五、常見誤區

- **不要**再用 `department_position.primary_user_id`（指定負責人）當作「往上一層找主管」的唯一依據。
  舊版 `eg_resolve_supervisor()` 第二步就是這樣寫的，而**這個欄位全站一筆都沒有設定**，
  所以那段程式從來沒成功過——組長以上一律回 `null`，呼叫端只好退回本人或最高決策者，
  這正是使用者看到「單位主管蓋自己的章」的根因。它現在只當同職級時的優先順序。
- **不要**用「職級比我高且最接近」當作單位主管的判定（舊版寫法）：課長 2、副課長 3、組長 3、副組長 3，
  同一階有好幾個職稱，嚴格比大小會讓副組長跳過同組的組長。判定基準是**「誰是這個單位的最高主管」**。
- **不要**在單據上把「單位主管」解析到課級以上。要讓廠長／總經理簽的是「核准」欄，那是另一個欄位、
  另一套規則（ai-rules/19）。
- **不要**假設「從缺」是錯誤或資料沒設好：課級單位的最高主管本人開單時，從缺就是正確答案。
