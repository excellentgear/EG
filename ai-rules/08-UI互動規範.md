## 零、表單設計總則（**所有**表單一體適用，2026-07-30 使用者明確要求）
做任何表單前先過這三條，違反其中任一條都算不合格：

1. **填寫方便性優先**：以「現場人員最快填完」為準則挑元件，不是以「程式好寫」或「資料最乾淨」為準則。同一件事若手打比選單快，就給手打（配格式寬容＋即時驗證），不要為了防呆把使用者鎖進難用的元件。判準：想像一個人一天要填 20 張，哪種方式手指動最少。
   - 反例（實際被使用者退回過）：時間欄做成「10 分為單位的下拉選單」——選項近百個要滾動找，比直接打 `0900` 慢得多。
   - 例外：**參照資料**（部門/人員/職稱/地點等主檔）仍一律下拉選擇，不可手打自由文字（見 memory `ui_reference_data_select`）；主檔沒有的值要能「當場新增進主檔後選用」，不要逼使用者放棄或亂打。
2. **畫面一致性**：同一種資料在全站用同一種元件、同一種格式、同一個位置語彙（日期＝月曆、時間＝直接輸入、參照＝下拉、數字＝無上下鈕）。同一頁內更不可一個欄位下拉、另一個手打。新頁面先找既有頁面抄元件，不要各自發明。
3. **錯誤即時偵測並說明原因**：驗證要在**輸入當下**（`input`/`change`）就跑，錯誤要「指出是哪個欄位、錯在哪、正確範圍是什麼」，不可以只在按送出時丟一句 `alert('資料有誤')`。
   - 呈現方式：出錯欄位加紅框（`.inv`）＋**該欄位旁/下方**一行紅字原因；多列表格則在該列的「檢查」欄顯示原因（可參考 `views/ADM/training_record.php` 的 `setErr()` / `dayValidate()`）。
   - 訊息要寫「為什麼錯」而非「不合法」：✅「小時 25 不存在，須 0~23」「結束 09:00 不可早於或等於開始 13:00」「日期與第 2 天重複」；❌「格式錯誤」「輸入有誤」。
   - 正在打字時只提示、不要改寫使用者輸入；**離開欄位（change/blur）才正規化**格式（例 `900`→`09:00`），否則游標會被搶。
   - **前端驗證不是防線**：後端同一組規則要再驗一次並回傳可讀原因（前端只是即時體驗）。

## 一、輸入欄位通用互動（四規則，**所有**輸入欄位一體適用）
1. **雙擊清空**：凡是有值的輸入欄位，滑鼠左鍵快速點兩下即清空內容。若該欄位同時是「篩選欄」（用來過濾列表的欄位），雙擊除了清空欄位本身，也要一併清除該欄目前套用的篩選條件（列表恢復成未套用該欄篩選的狀態；其他欄位的篩選不受影響）。
2. **Enter 逐欄前進、末欄送出**：在輸入欄位按 Enter，游標自動移至同一表單的下一個輸入欄；在**最後一個**輸入欄按 Enter＝送出表單（存檔）。多行文字框（textarea）內的 Enter 維持換行、不跳欄。
3. **聚焦自動全選**：點選（聚焦）已有資料的欄位時，自動全選其內容，方便直接覆寫修改。
4. **多列表格 ↑↓ 鍵切換欄位（2026-07-21 新增）**：畫面上「一列一筆、多列輸入」的表格（批次上傳列、逐列設定列等），按 ↑/↓ 鍵游標移至**上/下一列的同一欄**。若該表格有「新增列」按鈕（列數可增減，如 AS 文件「程序書快速建檔」的全部版本表格），另加兩個行為：在**最後一列按 ↓＝自動新增一列**；按 ↑ 離開的列若**完全未輸入**則自動移除該空列（第一列除外）。日期欄位必須攔截瀏覽器原生 ↑↓「改日數值」的行為改為移動列（列數固定的表格＝純切換，不增減列）。

這四條適用所有輸入欄位，不限數字框。數字輸入框除此之外還有專屬規則（無上下增減按鈕、小數尾0省略），那些是數字框額外加碼，不是取代通用規則。

## 二、日期欄位一律要有月曆選擇
任何需要使用者填寫日期的欄位，都要能點擊跳出月曆（date picker）選擇日期，不可以只提供讓使用者手動輸入文字。目的是避免格式不一致（`2026/7/13` vs `2026-07-13` vs 民國年 `115/7/13`）與手誤輸入錯誤日期。

**西元年限 4 碼（2026-07-16 新增）**：`<input type="date">` 未設 `max` 時瀏覽器允許年份到 6 碼（上限 275760 年），使用者連續鍵入時年份不會在 4 碼後自動跳到月份、會打出「202607」這種年。每個日期欄位一律加 `max="9999-12-31"`（有實際上限需求者用該上限）。全站已在 `views/partPage/sideAndTopBarMenu.html` 檔尾加共用 script 自動補此屬性（含動態產生的欄位，focusin 時補）——新頁面只要有 include 側邊欄就自動生效，不需重複實作；沒有 include 的獨立頁面才要自己加 max。

## 二之二、時間（時刻）欄位一律「直接輸入」，禁止下拉選時間（2026-07-30 使用者明確要求）
- 用 `<input type="text">`（非 `type=time`、非 `<select>`），寬容接受 `09:00`／`0900`／`900`／`9`／全形冒號，離開欄位時自動正規化成 `HH:MM`。
- **即時檢查合理性並說明原因**：小時 0~23、分鐘 0~59（`25:00` 要當下就報「小時 25 不存在，須 0~23」）；同一天的「結束時間」不可早於或等於「開始時間」（跨夜需求要另外明確設計，不可默默接受）。
- 有「時數」欄位時：開始時間＋時數↔結束時間互算，但**兩邊都要能手改**（實際上課/加工時數常與計畫不同；扣午休也要能自己改）。
- 多天/多列時間（多天課程、每日班別等）：提供「批次設定後套用到全部」＋「逐列個別修改」兩層，不可只有其中一種；批次套用不可覆寫使用者已個別調整過的日期。
- 可直接抄 `views/ADM/training_record.php` 的 `parseTime()`（回傳 `{ok,val}` 或 `{ok:false,msg}`）與 `dayValidate()`。後端另有 `tr_valid_time()`/`tr_norm_time()`（`src/store/Training_API.php`）同規則守門。

## 三、資料列表載入規則（含跨頁計算一定要後端先算好）

### 基本原則
- 頁面第一次載入時，**只**跟後端要「第 1 頁」需要顯示的那些列。
- 換頁、搜尋、套用篩選、改變每頁筆數 → 這些動作發生的當下才向後端要新的一批資料。
- 想讓換頁更順暢，可以在第 1 頁畫面顯示完成後，**背景**預先請求第 2 頁資料備用，但不可阻塞第 1 頁顯示，也不可以在使用者還沒操作前就把全部頁數一次載完。

### ⚠️ 最容易做錯的地方：跨頁彙總／排序／篩選，一定要後端先對全部資料算好
「只預載第 1 頁」指的是**列表逐列顯示的資料**要分頁載入，**不代表**任何需要看過全部資料才能得出的數字或順序也可以只看第 1 頁。以下情境都必須由後端在資料庫或程式裡對「全部符合目前篩選條件的資料」運算完，才把結果（含當前頁需要的那一小段）回傳給前端：

- **總計/彙總數字**：列表上方或下方顯示「總筆數、總金額、平均值」等，這些數字要用 `COUNT()`/`SUM()`/`AVG()` 等對全部符合條件的資料算好，跟第 1 頁資料一起回傳；**不可以**只加總第 1 頁那幾筆就當作總計（換頁後總計數字若沒有跟著變，通常就是算錯地方的訊號）。
- **依計算欄位排序**：若排序依據的欄位是 JOIN 多表或程式運算才得出的值（不是資料庫原始欄位），要先對**全部**符合篩選條件的資料排好序，再依當前頁碼切出對應那一段回傳；**不可以**只對「已經載入前端的那一頁」排序（結果會是錯的，且換頁後順序會跳動）。
- **依計算欄位篩選**：篩選條件若涉及這類運算欄位，也要在後端對全部資料算完再篩，不可以要求前端把所有頁面資料都載入後自己在瀏覽器裡篩選。
- **PDF/CSV 匯出**：匯出的是「目前篩選條件下的全部結果」，不是只匯出已經載入到前端的那一頁——匯出時後端要重新查一次全部符合條件的資料，不能依賴前端當下記憶體裡有哪些資料。

### 反面例子（禁止的寫法）
```
❌ 前端先把全部頁數的資料都 fetch 回來，才在瀏覽器裡用 JS 做排序/加總/篩選
   （這樣等於沒有分頁，初始載入一樣很慢，只是把慢的動作延後或藏起來）
❌ 總計數字用「目前顯示這一頁」的資料加總
❌ 排序鍵是運算欄位時，只對前端已載入的那一頁做 array.sort()
```

### 正確作法
```
✅ 後端 SQL／程式一次算完：WHERE 篩選 → 排序 → SUM/COUNT 彙總 → LIMIT 分頁
   → 回傳「這一頁的列 + 彙總數字 + 總筆數/總頁數」
✅ 前端只負責顯示回傳的這一頁與彙總數字；換頁/篩選/排序條件變更時重新呼叫後端
```

## 五、人員列表鐵則（**所有**會列出人員的地方一體適用，2026-07-30 使用者明確要求）
不論是設定頁勾選名單、下拉選單、簽核對象、排班、通知收件人、報表欄位，凡是列出「人」就必須遵守：

1. **只列未離職者**：判定欄位是 **`user.state`**（**不是** `user_status`！）。`state` 0=離職、90=特殊帳號(不列入員工) 一律不列；1=在職、99=最高權限帳號可列。
2. **長期請假者仍要列出，但必須標記「假別＋請假期間」**：留職停薪(state=2)、育嬰留停(state=3)，或有已核准且期間涵蓋今日、天數 ≥ 15 天的 `leave_request`。顯示格式：`留職停薪（2026-07-20 ~ 2026-10-20）`；只有 state 沒有假單時顯示`（期間未登錄請假單）`。
3. **一律依職稱排序並顯示職稱**：排序鍵＝`position.sort_order`（無職稱者排最後），列表要有「職稱」欄或在名字後加`（課長）`。**不可只按 user.id 或姓名排**。
4. **同一份列表若會出現不同部門的人 → 必須連部門一起顯示**（只有單一部門時可省略部門欄，避免多一欄雜訊）。

### 唯一實作點：`src/common/people_lib.php`（不要自己拼人員 SQL）
```php
require_once __DIR__ . '/people_lib.php';
$rows = eg_people_list($db, ['dept_ids' => $deptIds]);   // 也可傳 user_ids / states / keyword
$showDept = eg_people_multi_dept($rows);                  // 鐵則4：是否要顯示部門欄
// 每列可用：user_cname, position_name, dept_name, state_label,
//           on_leave(0/1), leave_label, leave_start, leave_end, leave_note, display
```
- 已排除離職／特殊帳號、已依職稱排序、已附長假標記；`display` 是現成的下拉文字（`高志宏（課長）［留職停薪（…）］`）。
- 常數：`EG_PEOPLE_EXCLUDE_STATES`（預設 `0,90`）、`EG_LONG_LEAVE_MIN_DAYS`（預設 15 天）。
- 一人掛多部門時，`eg_people_list` 會優先取「符合 dept_ids 篩選」→ 主要職務(`is_main`) → 最小 id 的那筆。

### 【症狀】【根因】【規則】
- 【症狀】品管部門人員名單多出一位已離職者（校驗人員資格 modal 顯示 6 人，實際在職 5 人）。
- 【根因】用 `COALESCE(u.user_status,0) <> 90` 當在職判定；`user_status` 不是在職欄位，離職是 `user.state=0`。
- 【規則】列人員一律 `eg_people_list()`，禁止各頁自己寫 `WHERE user...`；要判在職只看 `user.state`。
