> 前次 2026-07-23：新增「附件暫存機制」全站標準（新增單據未存檔就要能上傳）；合規範例補 personal_task_image。對應 CLAUDE.md 鐵律第 5 條。

## 為什麼要有這條規則
2026-07-13 盤點全站附件/圖檔路徑功能，發現同一件事本專案存在兩種做法，換 NAS 硬碟或搬資料夾時下場完全不同：

- **情況一（禁止再新增）**：上傳當下把「根路徑設定值＋子資料夾＋檔名」組成**完整絕對路徑**，直接寫死存進 DB。讀取/下載/刪除時直接拿 DB 存的那條路徑用。→ 換 NAS 磁碟代號或搬資料夾後，就算改了網頁設定，**舊資料的 DB 紀錄還是寫著舊路徑，會找不到檔案**，且無法只靠改設定修復，須額外寫 SQL 搬資料。
- **情況二（本規則要求的做法）**：DB 只存**檔名**（`file_name`），不存路徑。讀取/下載/刪除時，用「當前設定值的根路徑」＋「即時算出的子資料夾」現場組出完整路徑。→ 換 NAS 代號或搬資料夾後，只要把「資料夾＋檔名」原封不動複製過去、改一個設定值，**舊資料立刻能讀**，不用動 DB。

## 規則本身
**任何新功能，只要牽涉到「檔案存在磁碟/NAS 上、路徑會變動（尤其可能對應到 NAS）」，一律採情況二寫法：**

1. 資料表**不存完整路徑**。只存：`file_name`（實際存檔檔名，可含 timestamp/亂碼避免碰撞）＋（若原始檔名要留存）`original_filename`。
2. 根路徑存在 `system_settings`（或該模組既有的設定表，如報價單的 `system_parameters`），**不要寫死在程式碼**。
3. 子資料夾名稱（通常是單號、料號等）**不要另外存一份路徑欄位**——它本來就是這筆附件關聯的單據自己的欄位（外鍵可查到），現場需要時用該單據的當前值現場算，不要快取成路徑字串存起來。
4. 寫一個該模組專屬的「路徑解析函式」，例如：
   ```php
   function xxxAttResolvePath($db, array $row): string {
       $root = rtrim(getSetting($db, 'xxx_nas_dir', '預設值'), '\\/');
       $sub  = 現場算出的子資料夾（通常＝單號，規則需與上傳時一致）;
       return $root . DIRECTORY_SEPARATOR . $sub . DIRECTORY_SEPARATOR . $row['file_name'];
   }
   ```
   所有「下載/預覽/刪除/is_file/readfile/unlink/加註浮水印」的地方都呼叫這個函式，**不要**在多處各自重複組路徑邏輯（子資料夾規則以後若要調整，才只需要改一個地方）。
5. UNC 路徑（`\\主機\分享\...`）比磁碟代號（`Z:\...`）穩定，新設定值預設建議直接用 UNC；但這條規則本身**跟用 UNC 或磁碟代號無關**——不管根路徑字串長什麼樣子，「現場組路徑、不存絕對值」才是重點。UNC 相關的既有陷阱（不要對 UNC 根目錄 `is_dir()`/`is_writable()` 預檢、反斜線轉義等）見 `Z槽改UNC_提示詞與邏輯.md`。

## 全站統一附件根資料夾（2026-07-31 使用者明確要求，新模組一律照做）
**所有頁面的附件一律放在同一個 AS9100 根資料夾底下，各模組再以「頁面名稱」為子資料夾自動建立。**
- 根路徑預設 `\\excellentnas\AS9100維護\ERP AS9100文件(勿刪)`（設定鍵 `eg_attach_root`，改一處全站跟著搬）。
- 唯一實作點 `src/common/attach_lib.php`：
  ```php
  include_once __DIR__.'/attach_lib.php';
  $dir = eg_attach_dir($db, 'training_nas_dir', '教育訓練');  // 模組設定鍵優先；沒設定＝根路徑\教育訓練\
  if (!eg_attach_ensure_dir($dir)) { /* 回報「無法建立附件目錄」並中止 */ }
  $ok = move_uploaded_file($tmp, $dir . $fname);              // DB 只存 $fname
  ```
- **不要再各自寫死 `Z:/BOM/...` 當預設值**（舊模組已寫死的維持原狀，不必回頭改；它們的設定鍵有值就會優先採用，行為不變）。
- **不要再設 URL 前綴讓瀏覽器直連**：附件一律走該模組 API 下載（權限守門＋路徑現場組），UNC 路徑瀏覽器本來也連不到。
  可抄 `src/store/Training_API.php` 的 `download_attach`（依副檔名決定 inline/attachment，`filename*=UTF-8''` 支援中文檔名）。
- 目錄不存在要**自動建立**，不要叫使用者先去 NAS 開資料夾。

## 附件暫存機制 — 新增單據未存檔就要能上傳（2026-07-23 定案，全站附件功能一體適用）
使用者明確要求：**任何有附件的頁面，新增單據時就要能立刻上傳附件，不可以要求「先儲存單據才能上傳」**（附件需要主單 id 才能綁定，用暫存狀態機解決，不是用擋上傳解決）。標準做法（比照報價單與個人工作紀錄）：

1. 附件表除檔名欄外，加三欄：`user_id`（上傳者，temp 列以此判定擁有者）、`status VARCHAR(16) NOT NULL DEFAULT 'active'`（`temp`=未存檔暫存／`active`=正式）、`expire_at DATETIME NULL`（temp 自動清除到期時間）。
2. 上傳 action：主單 id=0（新增中）→ 存 `temp`＋`expire_at=NOW()+2天`＋`user_id=登入者`，立刻回傳 `img_id/url` 給前端顯示縮圖；主單 id>0 → 先驗擁有者/權限，直接存 `active`。
3. 前端把暫存上傳回傳的 id 記在陣列（如 `tempImgs`），按「儲存」時以 `temp_img_ids` 一併送出；後端在**主單儲存的同一筆交易內**轉正：`UPDATE 附件表 SET 主單id=?, status='active', expire_at=NULL WHERE id IN (...) AND user_id=登入者 AND status='temp'`。
4. 對外讀取（列表/單筆/檢視/匯出）一律只取 `status='active'`。
5. **懶惰清除**：列表 action 順路刪除已過期的 temp（實體檔＋DB 列各一次），不需要 Windows 排程。
6. 刪除附件的許可：正式附件走該模組原本的權限檢查；temp 附件限上傳者本人可刪。
7. 暫存與正式附件**同樣只存檔名**（本檔上方情況二規則），temp 不是例外。

可直接抄的範例：`src/store/PersonalTask_API.php`（`upload_task_image`／`save_task` 的 temp_img_ids 轉正／`pt_purge_expired_temp_images`，最精簡版）；`src/store/Quotation_File_API.php`（temp/active/pending/trash 四態進階版，含補件審核）。

## 例外與地雷（動手前必看）
- 若「子資料夾名稱」所依據的單號/料號**建立後可能被改名**，現場重組路徑會找錯資料夾——動手前務必確認該單號是否不可變（查程式碼有無改名功能，或直接問使用者），不確定就問，不要假設。
- 純本機 `uploads/` 目錄（非 NAS）的暫存檔案不受本規則約束（本來就在專案內，不會因換 NAS 而受影響）。
- 純「即時掃描資料夾比對」用途（不存 DB，只在頁面載入時 `scandir()` 找料號對應圖檔，如 `bom_viewer.php` 等一批圖面檢視頁）不是本規則要處理的對象——那批路徑是直接寫死在程式碼裡，屬於另一類問題，不要混為一談。
