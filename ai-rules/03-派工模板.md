# 派工 Prompt 模板
> 用法：主對話呼叫 Agent 工具時，複製對應模板、填掉【】即可。模型選擇見 [01-模型調度守則.md](01-模型調度守則.md) 第 4 節。
> 每份模板已內建：目標與動機／驗收條件／回報格式 三件套，以及本專案的巨檔保護規則。

## 通用尾巴（每個模板結尾都要帶）
```
環境注意：
- 專案路徑 c:\MAMP\htdocs\EGsystem，非 git repo。
- 超過 2000 行的檔案禁止整檔 Read：先 Grep 定位，再 Read offset/limit 讀 ±100 行。
- 執行 SQL 用：& C:\MAMP\bin\php\php8.3.1\php.exe C:\MAMP\htdocs\EGsystem\ai-rules\tools\sql.php "SQL"（一次一句；中文 SQL 用 --file）
- 回報只准包含：結論、檔案:行號、10 行以內的關鍵引文。長產物 Write 到【落檔路徑】後回傳路徑。
```

## 1. 搜尋／定位（subagent_type: Explore）
```
目標：找出【要找什麼，例：所有會寫入 stock_transactions 的程式位置】。
動機：【為什麼要找，例：接下來要在出庫時加通知，需要知道所有寫入點】。
範圍：c:\MAMP\htdocs\EGsystem 下的【views/、src/ 等】。
方法要求：至少用兩組不同關鍵字交叉搜尋（例：表名、欄位名、函式名），避免單一關鍵字漏抓。
驗收條件：每個結果附 檔案:行號 與一行說明該處在做什麼；最後明列「用過的搜尋關鍵字」讓我能判斷覆蓋度。
回報格式：條列，每條 = 檔案:行號 — 一句說明。找不到也要回報用過的關鍵字與結論。
```

## 2. 實作／修 bug（subagent_type: general-purpose）
```
目標：【要做什麼，例：在 views/pages/requisition.php 的出庫確認加上庫存不足擋掉】。
動機：【業務原因】。
已知定位：【檔案:行號、函式名、你已查到的線索——務必填，別讓 agent 從零掃】。
規格：【具體行為，含邊界：0/負數/小數/空值時怎樣】。
限制：
- 改檔前先備份：Copy-Item 檔案 檔案.bak-yyyyMMdd-HHmm
- 只能用 Edit，禁止 Write 覆寫既有檔案；不得改動無關程式。
- DB 寫入用 transaction；欄位名先 SHOW COLUMNS 確認。
驗收條件：
1. php -l 通過所有改過的檔。
2. 【可觀察的行為驗證，例：用 sql.php 造一筆庫存=2 的料，實跑出庫 5，確認被擋且庫存不變】。
3. 列出本次修改可能影響的 3 個既有功能與不受影響的理由。
回報格式：改了哪些檔（檔案:行號 + 各一句說明）、驗收 1–3 的實際結果、備份檔路徑。不要貼整段程式碼。
```

## 3. 重構／批次套用模式（subagent_type: general-purpose，通常 sonnet）
```
目標：把以下已驗證的修改模式套用到【檔案清單】。
樣板（已在【某檔】完成並驗證，照此模式做）：
【貼上完成範例的修改前/後片段】
逐檔步驟：備份 → Grep 定位【錨點關鍵字】 → Edit → php -l。
禁止：順手重構、改排版、動與模式無關的程式。看到與樣板不符、套不上去的檔案，跳過並記下原因，不要自行變通。
驗收條件：每個檔 php -l 通過；回報表格逐檔列出「已套用/跳過+原因」。
回報格式：表格（檔案｜狀態｜備份路徑｜備註），另列所有跳過檔案的原因。
```

## 4. 研究／技術調查（subagent_type: general-purpose；需要讀外部網頁時才用 WebSearch）
```
目標：回答【具體問題，例：PHP 8.3 + MySQL 9.4 下 PDO 連線偶發 2006 錯誤的可能原因與對策】。
動機：【現在卡住的實際狀況、錯誤訊息原文】。
方法要求：優先查本機事實（設定檔、log、實測），其次官方文件；每個結論註明依據（檔案路徑或網址）。區分「實測確認」與「文件推測」。
驗收條件：給出可執行的下一步（指令或修改），而不是泛論；如果查不到定論，明說查了哪裡、為何無定論。
回報格式：結論（≤5 行）→ 依據清單 → 建議下一步。全文落檔到【路徑】，回報只給摘要與路徑。
```

## 5. 審查／驗收（subagent_type: general-purpose，fresh context，勿附你的結論）
```
你是驗收者，你的價值在於找到問題；找不到問題也要說明檢查了哪些點。
需求原文：【使用者的原始要求】。
被驗對象：【改過的檔案清單與備份檔路徑（可用來 diff）】。
檢查項目：
1. 需求逐條對照：每條需求指出實作位置（檔案:行號）或標記「未實作」。
2. 用備份檔比對改動範圍：有沒有動到需求以外的程式？
3. 邊界：0/負數/小數/空值/無權限使用者 各會發生什麼？
4. 本專案鐵律：備份是否存在？巨檔是否被整檔覆寫過（檔案大小異常縮小 = 紅燈）？
5. 【可實跑的驗證步驟，例：curl 或 sql.php 查資料】。
回報格式：結論（通過/不通過）→ 問題清單（嚴重度排序，各附 檔案:行號 與失敗情境）→ 已檢查無誤的項目清單。
```
