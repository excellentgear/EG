# 17. 審核通知標準（通知上要能看完內容並直接決行）

> 2026-07-31 制定，使用者明確要求，**全站所有簽核／審核通知一體適用**（報價單、請假、採購、異常單、教育訓練計畫…）。
> 起因：審核者收到通知後還要自己去翻是哪一張單、附件在哪，等於通知只有「叫你去別的地方看」的功能。
> 相關：`ai-rules/11-代理系統設計.md`（誰該收到通知）、`ai-rules/07-附件路徑儲存規範.md`（附件路徑）、`src/common/approval_lib.php`（簽核紀錄）。

## 鐵則（違反＝不合格）

1. **通知上必須有「核准」與「退回」兩顆按鈕**，審核者不必再自己找頁面進去操作。
   （現行實作方式：通知點進去是該模組的「審核檢視頁」，兩顆按鈕就在頁面上；可抄 `views/Sales/quotation_approval_view.php`。）
2. **退回必須填寫原因**，不可空白退回；原因寫入 `approval_record.note`，並在單據頁與後續通知中原文顯示給送審者看。
3. **通知內要能直接看到表單／頁面內容**，不是只有一行「某某送出某單請簽核」：
   - 能用 HTML 呈現的，就把單據內容（表頭欄位＋明細表格）**完整**呈現在通知/審核檢視頁上。
   - 內容太長或本來就是紙本格式（列印版報表）而無法完整顯示者，**自動產生一份暫存附件（PDF/HTML）掛在通知上**供點開檢視——不可要求審核者自己去列印畫面看。
4. **單據本身的附件一律附在通知上**（可直接點開/下載），而且要**顯示附件標籤（類別）與附件的相關說明**（檔名、類別、備註、上傳者/時間），不可只丟一個檔名連結。
5. 決行後：**通知要自動結束**（`live_event.enddate` 往前設一天），不可讓已審完的通知繼續掛在置頂欄；並回發一則「已核准／已退回（原因）」通知給送審者。
6. 多段審核（審核 → 核准）**依序通知**：前一段核准後才通知下一段；任一段退回即整張退回給送審者重來，不可跳關。
7. 簽核紀錄一律寫 `approval_record`（`module` + `entity_id` + `level`），每次送審都是新的一列（保留完整歷史）；「誰有資格簽」的規則留在各模組。

## 檢查清單（做完自問）

- [ ] 通知點進去看得到**完整內容**（不是只有標題）？
- [ ] 有**核准**與**退回**按鈕？退回**強制填原因**？
- [ ] 單據附件**列在通知上**、可直接開、有**類別標籤與說明**？
- [ ] 內容無法完整顯示時，有**自動存成暫存附件**可開啟？
- [ ] 決行後舊通知**自動結束**、送審者**收到結果通知（含退回原因）**？
- [ ] 多段審核是**依序**通知，不是一次全發？
