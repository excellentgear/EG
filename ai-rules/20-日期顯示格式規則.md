# 日期顯示格式規則 — 西元年一律 YYYY.MM.DD

> 2026-08-06 使用者明確要求：全站任何**顯示給人看**的西元年日期（列表、表單、列印文件、跳窗文字），
> 一律用 `2026.08.06` 這種點分格式，不可再用 `2026-08-06`（dash）、`2026/08/06`（slash）等其他寫法。

## 適用範圍（只管「顯示」，不管「輸入/查詢/儲存」）

- ✅ 適用：畫面上的文字、表格欄位、列印文件、跳窗說明、Email/推播通知內文裡的日期。
- ❌ 不適用（維持原樣，不要改）：
  - `<input type="date">` 的 `value`（瀏覽器原生月曆元件本來就吃 `yyyy-mm-dd`，改了會壞掉）。
  - SQL 查詢條件（`WHERE xxx_date BETWEEN ? AND ?`）與 DB 寫入值（`INSERT`/`UPDATE` 存的日期欄位）。
  - AJAX 請求參數（前端送給後端的日期字串，後端各種比對邏輯預期的是 `Y-m-d`）。
  - 民國年/農曆等本來就不是西元年顯示的欄位（不在本規則範圍內）。

## 唯一實作（禁止各頁自己再寫一份 fmtDate/formatDate）

- **JS**：`resource/js/eg_date_fmt.js` 的 `egFmtDate(d, withTime)`。頁面載入方式（放在 `custom.min.js` 之後）：
  ```html
  <script src="../../resource/js/eg_date_fmt.js?v=<?= @filemtime(__DIR__.'/../../resource/js/eg_date_fmt.js') ?>"></script>
  ```
  頁面若已有自己的 `fmtDate(d){...}` 包裝函式，不用整個拔掉，改成內部呼叫 `egFmtDate(d)` 即可（呼叫端不用改，風險最低）。
- **PHP**：`src/common/date_fmt_lib.php` 的 `eg_fmt_date($d, bool $withTime=false)`。
  ```php
  require_once __DIR__.'/../../src/common/date_fmt_lib.php';
  echo eg_fmt_date($row['audit_date']);          // 2026.08.06
  echo eg_fmt_date($row['created_at'], true);    // 2026.08.06 14:30
  ```
- 兩邊輸出格式必須一致（互為對照組），改動任一邊要同步檢查另一邊。

## 判斷「這是顯示還是查詢/儲存」的簡單方法

- 這個字串最後會不會被拿去 `WHERE`、`INSERT`、`UPDATE`、當成 AJAX 參數送出、或塞進 `<input value>`？會 → 不要動。
- 這個字串最後會不會直接印在畫面/列印文件上給人看？會 → 要用 `egFmtDate()`/`eg_fmt_date()`。
- 同一支檔案裡兩種用途常常混在一起（例如同一個 `date()` 呼叫結果，一份存 DB 一份印畫面），要分開看每個呼叫點，不要整支檔案一次批次取代。

## 既有頁面適用範圍（不強迫全站一次改完，比照 `eg_input_rules.js` 基準線模式）

**新頁面／新功能一律必須用唯一實作。** 既有頁面採**先處理「有綁定 AS 文件編號」的頁面**（2026-08-06 使用者明確指示的優先順序），其餘頁面之後陸續碰到再順手改，不強迫一次全站掃完（本專案已知有 ~50-70 支檔案、150+ 處分散的 `date('Y-m-d')`/`->format('Y-m-d')`/JS 字串拼接寫死格式，且與 SQL 查詢用途混在一起，全面掃描成本過高、且容易誤改到查詢用途造成功能壞掉）。
