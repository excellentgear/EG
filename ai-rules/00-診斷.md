# 快速診斷：本環境三大風險與修法
> 寫於 2026-07-06（Fable 5 制度建立 session）。後面所有規則檔都以這份診斷為依據。
> 讀者：未來在此專案工作的 AI session（Sonnet / Opus / Haiku 等級）。
> 最後修改：2026-07-22 — 修正備份陷阱（改用 git，取代已過時的「非 git repo」條目）；新增「本機同時裝 3 套 MySQL，port 別接錯」陷阱。

## 風險一：巨型單檔（最漏 token、也最容易毀檔）

**事實**（2026-07-06 實測）：
- views/ 共 125 個 PHP 檔、合計 13.1MB
- `views/pages/master_data_management.php` = **1.5MB**（實測 21,951 行）
- `views/pages/stock.php` = 721KB、`views/Sales/NewOrder_Track.php` = 745KB
- 這種檔案整檔讀入 ≈ 20–40 萬 token，**一次就撐爆 context**；用 Write 整檔覆寫必然截斷毀檔。

**修法（強制流程，寫入 CLAUDE.md 鐵律）**：
1. 禁止對超過 2000 行的檔案做整檔 Read；禁止對任何既有檔案用 Write 整檔覆寫（只能用 Edit）。
2. 巨檔修改流程：`Grep 找關鍵字定位行號` → `Read 該行號 ±100 行` → `Edit 用唯一錨點修改` → `php -l 檢查語法`。
3. Edit 錨點務必夠長（含前後各 2–3 行原文），巨檔內重複片段極多，短錨點會撞到多處。
4. 改巨檔前確認 `git status` 乾淨（上一版已 commit）；改完 `php -l` 通過就立刻 commit+push（2026-07-14 起本專案已用 git 版控，不再手動 `.bak` 備份，見 CLAUDE.md 鐵律1、6）。

## 風險二：主對話自己下場掃庫（最漏 token、最容易失焦）

**事實**：主對話每讀一個大檔、每掃一輪 repo，這些內容就永久佔據 context；長對話後早期規則（備份、change_log、權限同步）被擠出注意力，就是「失焦」的機制。

**修法**：
1. 指揮官不下場：大量搜尋/讀檔/掃 repo/查網頁 → 派 subagent（Explore 或 general-purpose），主對話只收「結論 + 檔案:行號」。細則見 [01-模型調度守則.md](01-模型調度守則.md)。
2. 主對話允許自己做的事：讀單一小檔（<500 行）的目標區段、做 Edit、跑指令、與使用者對話。
3. 每完成一個修改就立刻執行收尾 checklist（見 CLAUDE.md），不要累積到對話尾端才做——尾端正是最健忘的時候。

## 風險三：環境陷阱（最容易出錯）

**實測過的陷阱與解法**：

| 陷阱 | 症狀 | 解法 |
|---|---|---|
| 舊版 mysql CLI 連不上 MySQL 9.4 | `SSL connection error` / `caching_sha2_password` 錯誤 | **不要用** `C:\MAMP\bin\mysql\bin\mysql.exe`。一律用 `C:\MAMP\bin\php\php8.3.1\php.exe C:\MAMP\htdocs\EGsystem\ai-rules\tools\sql.php "SQL"`（已驗證可用，中文正常） |
| PowerShell 5.1 沒有 `&&` `\|\|` | parser error | 用 `A; if ($?) { B }`，或改用 Bash 工具 |
| PowerShell 寫檔預設 UTF-16 BOM | PHP/SQL 讀到亂碼或第一行報錯 | 寫檔一律用 Write 工具；不得已用 PS 時加 `-Encoding utf8` |
| 命令列直接帶中文參數 | 中文變亂碼 | 中文 SQL 用 `sql.php --file` 方式；中文內容先用 Write 落檔再引用 |
| user 表 latin1 欄位 | 錯誤 1366/3854、中文 LIKE 查不到 | 查詢時 `CONVERT(欄位 USING utf8mb4)`；細節見記憶 db_charset_constraints |
| 欄位名靠印象猜 | SQL 錯或寫錯欄位 | 動 SQL 前先 `SHOW COLUMNS FROM 表` 或查 `MYSQL 資料字典.txt`（用 Grep 查，該檔 196KB 不要整讀） |
| 這台機器同時裝了 3 套 MySQL/MariaDB，容易接錯引擎 | 系統層級（非透過 EGsystem 程式）操作 DB 時，port 猜錯會連到別套資料庫 | **EGsystem 固定用 port 3306 = 官方 MySQL 9.4（Windows 服務 `MySQL94`，路徑 `C:\Program Files\MySQL\MySQL Server 9.4\`，datadir=`C:\ProgramData\MySQL\MySQL Server 9.4\Data\`）**。另外還有 port 3307=MAMP 內建 MySQL（`C:\MAMP\bin\mysql\`）、port 3308=MariaDB 11.8（`C:\Program Files\MariaDB 11.8\`），兩者都跟 EGsystem 無關，不要動。磁碟上還有 `C:\laragon\` 但目前無監聽行程，屬閒置。2026-07-22 用 `SHOW VARIABLES LIKE 'datadir'`（透過 sql.php，最權威）+ Windows 行程 parent-PID 追查雙重驗證確認，見記憶 `mysql_engine_confirmed` |
| 新頁面側邊欄無法展開 | 選單點了沒反應、console 出現 run_charts 等 log 但選單不動 | Gentelella 版型頁面底部必須依序載入 `jquery.min.js`→`bootstrap.min.js`→`custom.min.js`（缺 custom.min.js 選單就死）。照抄 views/QC/inspection_combined_prototype.php 底部三行 |
| 置頂欄/側邊欄整片不可點擊（無 console 錯誤） | 看得到但點不動，重新整理也一樣 | 兩個已實測根因：(1) 對全寬元素（如 .page-title）加 position:relative+z-index 會蓋住頂欄/側欄可點區 → z-index 只加在小元素（如 .btn-group），並給 .top_nav/.left_col 更高 z-index 保險；(2) Bootstrap3 Modal「關閉後立即開另一個」會殘留透明 backdrop 擋全頁 → 換窗要用 `.one('hidden.bs.modal',...)` 等關完再開，並掛全域 hidden 清 backdrop 安全網（範例見 views/QA/correction_order.php） |

## 本診斷的使用方式
- 新 session 不需要重讀本檔全文；CLAUDE.md 的鐵律已內含以上修法。
- 當你想「為什麼要這樣規定」時，回來讀這份。
- 發現新陷阱：實測確認後補進上表，並照 [04-維護協議.md](04-維護協議.md) 的格式記錄。
