# 職務調動連動檢查 製作說明（給 AI）
> 建立：2026-07-29。動工前必讀。與 [ai-rules/11-代理系統設計.md](11-代理系統設計.md)、[ai-rules/12-請假系統製作說明.md](12-請假系統製作說明.md) 綁定。
> 讀者：要實作／修改「員工部門・職位異動」及其連帶影響（代理人、權限、指定負責人、簽核鏈）的 AI session。

## 0. 為什麼要做（真實事故）
2026-07-29 使用者回報請假頁「顯示尚未設定職務代理人」。追查結果：

- `user_delegate` 有設定，但 `end_date` 停在 `2026-01-01` ——**因為當初職務調動，人事把代理「終止」了，之後就沒有人記得要重設**。
- `position_delegate`（職稱代理）有 23 筆，但 `department_position.primary_user_id` **69 筆全為 NULL**，所以職稱代理永遠解析不出實際的人。

**結論：異動當下少做的每一件事，都會在幾個月後變成「功能好像壞了」的客訴，而且很難追出原因。**
本規範的目的＝**讓「調動後該改什麼」變成系統會主動列出、可勾稽、可事後追溯的清單，而不是靠人記得。**

## 1. 現況（先讀，別重做）
| 已經有的 | 位置 | 做到哪 |
|---|---|---|
| 異動阻擋式確認 | `src/store/_employee_api.php` 第 271 行起（P4） | `update` 時若移除某職務身分，偵測會失效的 **scoped 代理** 與 **此人擔任的指定負責人**，未確認回 `need_confirm` 擋下；確認後於同交易 `active=0` 停用。此人**作為代理人**的設定僅提醒複查。 |
| 稽核表 | `audit_log`（action_type / target_type / target_id / target_name / changes(JSON) / operator / created_at） | 代理與 SoD 事件已在寫（`DELEGATE` / `SOD_ESCALATE`）。**職務調動本身目前沒有寫。** |
| 在職狀態歷程 | `user_status_history`（user_id / status / start_date / end_date / remark） | 只記 `state` 變化（離職、留停），**不記部門職位變化**。 |
| 代理到期提示 | `views/ADM/hr_settings.php` 使用者代理設定區 | 逐列「已到期」標籤＋整區彙總提醒＋「只看已到期」篩選（2026-07-29 加）。 |
| **在職狀態封鎖** | `src/common/user_active_lib.php`（2026-07-30 加） | `user.state ∈ (0離職,2留停,3育嬰留停)` 者：不能登入、線上中翻頁即被踢出、`rf_*` 一律回空功能碼。**判斷時擋、不動資料**（誤設/回鍋改回狀態即復原）。權限資料清除是另一支 `eg_revoke_user_permissions()`，由人事按鈕觸發，清除前寫 `audit_log(PERM_REVOKE)`；代理只停用不刪，職務歸屬(`user_department_position_map`)保留供歷史單據查詢。**新做任何權限判斷都不必自己查 state，呼叫 `eg_user_is_active()` 即可。** |

**缺的就是本規範要補的三件事：異動紀錄、連動點檢表、前後對照。**

## 2. 使用者定調的實務前提（照做，別自行推翻）
1. **辦公室**人員需要**職位一對一代理**；且**主職位與兼任職位的代理人可能是不同人**（對應 `user_delegate.scope_department_id` + `scope_position_id`）。
2. **現場**人員大多**不需要代理人**（主管會直接安排工作）；**只有主管需要代理人**。
3. 因此**不可**用「同部門同職稱任一人」自動代入當代理人——那不符合一對一的要求。
4. 沒有代理設定＝此職務不需代理，**不可因此擋住請假**（已於 2026-07-29 修正）。

## 3. 要做的三塊

### 3.1 職務調動紀錄（必要，先做）
新增表 `user_position_history`（名稱可調，但**不要**塞進 `user_status_history`，那張是在職狀態用的）：

| 欄位 | 說明 |
|---|---|
| `id` | PK |
| `user_id` | 異動對象 |
| `change_type` | `transfer`(部門/職位異動) / `concurrent_add` / `concurrent_remove` / `resign` / `reinstate` |
| `before_json` | 異動前的完整職務身分快照（主職＋所有兼任：`[{department_id,department_name,position_id,position_name,is_main}]`）**名稱要一起存**，日後部門改名仍看得懂當時狀況 |
| `after_json` | 異動後的同格式快照 |
| `effective_date` | 生效日（預設今天，可由人事指定；追溯調動用） |
| `reason` | 異動原因（人事填，選填） |
| `checklist_json` | 連動點檢表狀態（見 3.2） |
| `checklist_done_at` | 點檢全部完成的時間；NULL＝仍有未處理項 |
| `operator_id` / `operator` / `created_at` | 誰在何時做的 |

**寫入時機**：`_employee_api.php` 的 `addOrUpdateEmployee('update')` 內，**與職務 map 的變更在同一個 transaction**。既有的 P4 檢查已經在算「移除了哪些身分」，把 before/after 快照順手一起存即可，不必另外查一次。

同時寫 `audit_log`：`action_type='POSITION_CHANGE'`、`target_type='user'`、`target_id=user_id`、`changes` 存 `{before, after, effective_date}`。**兩邊都寫**：`audit_log` 供全站稽核查詢頁一致檢索，`user_position_history` 供本功能的點檢表掛載。

### 3.2 連動點檢表（核心）
異動存檔成功後，**不要只跳「已儲存」**，要跳出「此次調動需要一併確認的項目」，每項可勾選「已處理／不需處理」，未處理的持續顯示在待辦。

**自動偵測的項目（能自動判定的就別讓使用者猜）**：

| # | 檢查項 | 偵測方式 | 自動可做的處置 |
|---|---|---|---|
| 1 | 此人作為**被代理人**的 scoped 代理失效 | `user_delegate WHERE user_id=? AND (scope_department_id,scope_position_id)` 落在被移除的身分 | 已由 P4 停用；點檢表列出並要求**重設新職務的代理** |
| 2 | 此人**作為代理人**的設定是否仍合理 | `user_delegate WHERE delegate_id=? AND active=1` | 不自動停（可能仍合理），**必須人工判定**；列出「他現在代理誰、以什麼身分」 |
| 3 | 此人擔任的**部門×職稱指定負責人** | `department_position WHERE primary_user_id=?` | 舊身分的要清掉或改人；**新身分若該格 primary_user_id 為 NULL，提示是否指定為他** |
| 4 | **RBAC 角色**是否需調整 | `user_roles` 現有角色 vs 新職務常見角色；並列出 `position_roles`（職稱指派）因換職稱而**自動增減**的功能碼 | 職稱指派的部分是自動生效的，**要明白告訴使用者「他因此多了/少了什麼權限」**，這是最容易被忽略的一項 |
| 5 | **簽核鏈**是否斷掉 | 用 [11] 的 `eg_resolve_supervisor()` 對「原部門的下屬」重算一次；若某人因此解析不到主管，列出 | 提示補設 `department_position.primary_user_id` 或最終裁決者 |
| 6 | 進行中的**待簽單據** | 各模組 `approval_record` / `leave_approval` / `as_form_approval` 中 `approver_id=? AND status='pending'` | 列出「他還有 N 張單待簽」，提示改派或請他先簽完 |
| 7 | **排班**是否要調整 | `roster_shift_assign WHERE user_id=? AND work_date>=生效日` | 列出未來已排的班，提示是否移轉 |
| 8 | 請假系統**主管鏈**影響 | 若他是主管：其部屬的請假第一層簽核人會改變 | 純提示，無需動作 |

**點檢表 UI 要求**：
- 每列：項目名稱、**自動抓到的前後對照**（例：`業務部/組員 → 生產2廠/組長`；`失去功能碼 quotation_edit、取得 roster_manage`）、狀態（待處理／已處理／不需處理）、快速動作連結（直接跳到該設定頁並帶參數）。
- **能自動算的一律自動算好**，使用者只需確認；不要做成空白待辦讓人自己想。
- 全部處理完 → 寫 `checklist_done_at`；未完成的**掛到人事的待辦提醒**（順路觸發，不發推播洗版，比照 [12] 的通知紀律）。
- 點檢表可事後重開（從調動紀錄清單點進去），**不是一次性跳窗關掉就沒了**。

### 3.3 前後對照（`before_json` / `after_json`）
- 快照**存名稱不只存 id**：部門/職稱改名後，舊紀錄仍要看得懂。
- 顯示用共用函式產生「差異摘要」字串（新增/移除/變更各一行），列表與點檢表共用同一份邏輯，不要各寫各的。
- 權限差異（第 4 項）同理：比對異動前後的 `rf_load_user_features_override()` 結果，列出**新增**與**失去**的功能碼，並附中文說明（功能碼→說明的對照，各模組頁面內已有 `$PAGE_FEATURES` 可重用）。

## 4. 鐵律
1. **紀錄與職務變更同一個 transaction**：不可先存人事資料、事後補寫紀錄（中途失敗會留下無紀錄的異動）。
2. **點檢表不可阻擋存檔**（P4 既有的「代理失效」確認才擋）：調動本身要能先完成，點檢項目變成待辦。否則人事會被卡住而繞道改 DB。
3. **不可自動改權限**：角色調整一律列出建議、由人確認。權限自動增減只有 `position_roles`（職稱指派）本來就會發生，那是**告知**不是變更。
4. **代理不可自動猜人**：見 §2.3。只能提示「請重設」，不可自動指派同職稱同事。
5. 沿用既有基礎：代理解析一律 [11] 的 `eg_resolve_signer()` / `eg_resolve_supervisor()`；稽核寫 `audit_log`；**不要新開一套權限或代理表**。
6. 收尾照 CLAUDE.md 鐵律6（`php -l`、commit+`git pushall`、`page_change_log`、新頁面要登記選單與角色區塊、跑 `check_sidebar.php`）。

## 5. 建議實作順序
1. **P1** `user_position_history` 建表 ＋ `_employee_api.php` 在既有 P4 交易內寫入 before/after 快照 ＋ `audit_log` 一併寫。（此步做完就已經「留有紀錄」，價值最高）
2. **P2** 點檢表偵測邏輯抽成 `src/common/position_change_lib.php`（純函式：給 user_id 與 before/after，回傳 8 項檢查結果），先做 1/2/3/4 項。
3. **P3** 人事端 UI：異動存檔後跳點檢表；調動紀錄清單頁（可重開點檢表、看前後對照）。
4. **P4** 補 5~8 項（簽核鏈、待簽單據、排班、主管鏈影響）＋未完成點檢的順路提醒。

## 6. 動工前要問使用者的事
- 點檢表的**負責人**是誰：人事自己勾，還是要通知各單位主管確認？
- 未完成的點檢要**提醒多久**、用什麼方式（順路提醒／每週彙總／不提醒只留紀錄）？
- **追溯調動**（生效日早於今天）要不要支援？若要，已產生的簽核/請假紀錄是否需要重算？
- 權限建議要不要做到「一鍵套用建議角色」，還是只列出、人工到權限頁改？
